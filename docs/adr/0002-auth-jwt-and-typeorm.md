# ADR 0002 — Авторизація: JWT у httpOnly-cookie і TypeORM у шарі інфраструктури

- **Статус:** Прийнято
- **Дата:** 2026-08-26
- **Контекст рішення:** перша фіча — `auth`
- **Уточнює:** [ADR 0001](0001-initial-setup.md), пункти 6 (сесії) і «Розглянуті
  альтернативи» (рядок про Prisma)

## Контекст

ADR 0001 закріпив сесійну авторизацію на httpOnly-cookie і відмовився від ORM
(«домен має лишатися вільним від ORM-типів»). Технічне завдання на фічу `auth`
натомість називає **JWT** і **TypeORM** прямо.

Суперечність тут менша, ніж здається, бо обидва документи говорять про різне:

- ADR 0001 відхиляє не JWT як формат, а **JWT у localStorage** — і причина в
  ньому названа: XSS-поверхня без жодної переваги, бо SPA і API живуть на
  одному домені.
- Заперечення до ORM стосується **домену**, а не доступу до даних узагалі.

Є і третя обставина, суто технічна: бекенд не збирається — Node 26 стирає типи
й виконує `.ts` напряму. Декоратори (`@Entity`, `@Column`) не стираються, їх
треба трансформувати, і `erasableSyntaxOnly` забороняє їх на рівні `tsc`.
Класичний спосіб описувати сутності TypeORM у цьому проєкті недоступний.

## Рішення

### 1. Токен у форматі JWT, транспорт — httpOnly-cookie

Сесія — підписаний HS256 JWT (`jose`), який їде у cookie
`mouse_session; HttpOnly; SameSite=Strict; Secure` (Secure — у проді). Ні
`Authorization: Bearer`, ні localStorage, ні sessionStorage.

Причина: вимогу «JWT» задовольняє формат токена, а не спосіб його зберігання.
Cookie при цьому лишається тим самим механізмом, який обрано в ADR 0001:
JavaScript токена не бачить, кросдоменні заголовки не потрібні, CORS не
з'являється ніде — ні в проді (Caddy), ні в dev (проксі `ng serve`).

Прапорець «запам'ятати мене» керує саме cookie: без нього вона сесійна й вмирає
разом із вкладкою, з ним отримує `Max-Age` (30 діб проти 72 годин базових —
константи в `config.ts`).

### 2. Ревокація через `tokens_valid_from`, а не список відкликаних токенів

Головна вада stateless-JWT — logout, який нічого не скасовує. Замість таблиці
відкликань у `users` є колонка `tokens_valid_from`: logout зсуває її в «зараз»,
а перевірка сесії відхиляє токен, у якого `iat` менший за це значення.

Причина: адмінка й так читає користувача з БД на кожному захищеному запиті —
без цього деактивація акаунта діяла б лише після протермінування токена. Раз
похід у базу вже є, ревокація коштує одну колонку й одне порівняння, а не нову
таблицю з власним прибиранням.

### 3. TypeORM живе тільки в `*.repository.ts` і `*.entity.ts`

Домен (`user.ts`), порти (`auth.port.ts`) і use-case'и не імпортують `typeorm`
взагалі — це перевіряє правило `ports-and-domain-have-no-io` у
`.dependency-cruiser.cjs`. ORM видно рівно двом файлам модуля.

Причина: заперечення ADR 0001 стосувалося протікання ORM-типів у домен, і воно
лишається чинним. Тестам це видно безпосередньо: усі юніт-тести `auth`
працюють на in-memory реалізаціях портів, без Postgres і без контейнера.

### 4. Сутності через `EntitySchema`, без декораторів

`user.entity.ts` — це звичайний обʼєкт `new EntitySchema<User>({...})`.

Причина: декоратори не стираються, а стираність — умова того, що бекенд
обходиться без збірки (ADR 0001, п. 7). `EntitySchema` дає ту саму типізацію
через дженерик `<User>`, тільки без синтаксису, який довелося б компілювати.
Побічно це навіть краще: мапінг лежить окремо від доменного типу, а не
нашаровується на нього анотаціями.

### 5. `CREATE DATABASE` — не міграція

Базу `mouse_trading` створює `apps/api/db/init/0001-create-database.sql`:
у dev його проганяє контейнер `postgres` при першій ініціалізації тому, на
наявному сервері — `npm run db:create`.

Причина: `CREATE DATABASE` не виконується всередині транзакції (а міграції
TypeORM транзакційні) і потребує зʼєднання з *іншою* базою — до тієї, яку
створюють, підключитися ще неможливо. Схему всередині бази створюють уже
звичайні міграції.

### 6. Міграції перелічені явно, а не знайдені glob'ом

`db/migrate.ts` імпортує класи міграцій списком.

Причина: порядок застосування видно в діффі, а рантайм не залежить від того, чи
вміє завантажувач ORM читати `.ts` без збірки. Ціна — рядок, який дописують
руками; про нього нагадує `npm run db:migrate:new`.

## Наслідки

- Вимога ТЗ виконана, а властивість, заради якої ADR 0001 обирав cookie
  (токен недосяжний для JavaScript), збережена.
- Домен лишається без ORM-типів, тож обіцянка «тестуємо без інфраструктури»
  підтверджується запуском: 25 тестів бекенду не піднімають Postgres.
- Зміна `JWT_SECRET` знецінює всі активні сесії — це навмисно й це аварійний
  вимикач.
- Кожен захищений запит робить `select` користувача. При одному-двох адмінах це
  дешевше за будь-який кеш; якщо запитів стане багато, кешується сам користувач,
  а не рішення про токен.
- `SameSite=Strict` означає, що перехід за посиланням із зовнішнього сайту
  вимагатиме повторного входу. Для внутрішньої адмінки прийнятно.

## Розглянуті альтернативи

| Варіант | Чому відхилено |
|---|---|
| JWT у localStorage + `Authorization: Bearer` | Саме те, що відхилив ADR 0001: XSS читає токен, а переваги нема — домен один |
| Непрозорий session id у таблиці `sessions` | Формально ближче до ADR 0001, але ТЗ називає JWT; при цьому колонка `tokens_valid_from` дає ту саму ревокацію без окремої таблиці |
| Refresh-токен + короткий access | Пара токенів має сенс проти вкраденого access у чужому сховищі; httpOnly-cookie цієї загрози не має, а складність додає одразу |
| Декоратори TypeORM + `tsc`/SWC для бекенду | Повертає крок збірки, який ADR 0001 прибрав свідомо, — і заради синтаксису, а не функціональності |
| Query builder / чистий `pg` замість TypeORM | Ближче до «тонкого шару запитів» з ADR 0001, але ТЗ називає TypeORM; ізоляція в двох файлах знімає ризик, заради якого ORM відхиляли |
| Валідація токена без походу в БД | Дешевше, але logout і деактивація акаунта починали б діяти лише після протермінування токена |
