# ADR 0001 — Початкова архітектура системи

- **Статус:** Прийнято
- **Дата:** 2026-08-18
- **Контекст рішення:** старт проєкту `mouse.springconsult.com.ua`
- **Переглянуто:** пункт 7 (бекенд без збірки) і шари всередині модуля —
  [ADR 0003](0003-three-layer-classes.md) додав крок збірки `tsc` і замінив
  `routes → use-case → port ← repository` на `Controller → Service → Repository`.

## Контекст

Підготовка карток комісійних товарів для Prom та OLX виконується вручну: фото
завантажується в AI-чат для розпізнавання, окремим запитом генерується SEO-опис,
ще одним — додаткові SEO-тексти, ще одним — пошук реалістичних цін на схожі товари
в Україні. Результат зберігається теками на локальному компʼютері й вручну
переноситься на маркетплейси.

Обмеження, які формують рішення:

- Обсяг — 50–100 товарів на місяць. Це мало: система не має бути розподіленою.
- Користувачів — один-два адміни. Складна авторизація не потрібна.
- Витрати на AI прямо залежать від розміру зображень і від зайвого форматування
  у відповідях, тож економія токенів — вимога, а не оптимізація.
- Наступний етап — автоматична синхронізація з маркетплейсами. Архітектура має
  прийняти її без переписування.
- Розробка й підтримка — силами однієї людини. Кількість рухомих частин критична.

## Рішення

### 1. Модульний моноліт з портами й адаптерами, розгорнутий у кількох контейнерах

Одна кодова база `apps/api`, один Docker-образ, дві точки входу: `api` (Fastify) і
`worker` (обробник черги). Бізнес розбитий на вертикальні модулі
(`auth`, `products`, `media`, `ai`). Шари всередині модуля — `routes → use-case → port
← repository/adapter` — позначені суфіксами файлів, а не каталогами: на цьому масштабі
чотири вкладені папки на модуль коштують більше уваги, ніж дають ясності.

Причина: мікросервіси при 100 товарах на місяць коштують більше, ніж дають —
мережеві межі, окремі деплої, розподілені транзакції. Водночас межі всередині
коду потрібні вже зараз, бо синхронізація з маркетплейсами додаватиметься пізніше
й не повинна змусити переписувати `products`. Порти й адаптери дають ще одну практичну
властивість: домен тестується без Postgres, R2 і Anthropic API.

Розділення на два процеси — не архітектурне, а операційне: розпізнавання фото
триває десятки секунд, і воно не має жити в HTTP-запиті. Той самий образ,
різна команда запуску — один реліз, спільні типи, спільні міграції.

### 2. Черга задач у PostgreSQL (pg-boss), без окремого брокера

Довгі операції — sharp-конвеєр, виклик Claude, пошук цін — виконуються
асинхронно. Замість Redis чи RabbitMQ використовується pg-boss в окремій схемі
тієї самої бази.

Причина: при цьому навантаженні брокер — це зайвий контейнер, зайва точка відмови
і зайвий бекап. Postgres уже в системі та обов'язковий; стан задачі й стан товару
лежать в одній транзакційній базі, і це прибирає цілий клас розсинхронів. Якщо
навантаження виросте, pg-boss замінюється без зміни доменного коду — черга
захована за портом.

### 3. Зображення в Cloudflare R2, оптимізація до AI обов'язкова

Оригінал і похідні (`ai`, `card`, `thumb`) лежать у R2; у БД — тільки ключі,
порядок і метадані. Перед відправкою в AI кадр проходить sharp: довша сторона
≤ 1568 px, JPEG q80, sRGB, EXIF вирізано. У розпізнавання йде щонайбільше 3 кадри;
додаткові фото зберігаються **без** участі AI.

Причина: кадр оплачується візуальними токенами пропорційно до площі. `claude-opus-5`
приймає до 2576 px по довшій стороні (до ~4784 токенів на зображення), але для фото
товару на нейтральному тлі така деталізація нічого не додає: 1568 px дають те саме
розпізнавання помітно дешевше. Це вибір ціни, а не технічна межа моделі — якщо
якості забракне, межа піднімається після заміру через `count_tokens`. R2 обрано
через відсутність плати за
egress: галерея товарів віддається браузеру напряму, API не проксує байти.

### 4. `claude-opus-5` зі structured outputs; ціни — через server tool web search

Розпізнавання та генерація текстів — один виклик `claude-opus-5` з adaptive
thinking. Відповідь запитується за JSON-схемою (`output_config.format`) і
зберігається як plain text. Ринкові ціни шукає server tool `web_search_20260209`
з локацією UA; кожна генерація пише `usage` у таблицю `ai_generations`.

Причина: structured outputs прибирають два джерела витрат одночасно — модель не
генерує Markdown, емодзі й ввічливі обгортки, а бекенду не потрібен парсер
вільного тексту. Тексти й так редагуються в звичайному `textarea`, тож форматування
не має де знадобитися. Пошук цін на боці Anthropic знімає потребу в окремому
пошуковому API і власному скрапінгу. Облік `usage` робить собівартість картки
вимірюваною з першого дня.

### 5. Спільні контракти в `apps/api/src/contracts/`, без окремого пакета

Zod-схеми лежать усередині API. Бекенд валідує ними вхідні дані, фронт імпортує з
них типи через tsconfig alias `@contracts/*`.

Причина: типова помилка Angular + Node — два незалежні описи однієї відповіді, які
розходяться після першого ж рефакторингу; спільний файл це знімає. Але робити з
нього npm-пакет не варто: Node не стрипає типи у файлах всередині `node_modules`,
а workspace-симлінк саме ним і виглядає, тож пакет довелося б компілювати в JS —
і він став би єдиним build-кроком у проєкті, який інакше обходиться без збірки.
Рівноправний пакет посередині ще й моделює неіснуючу симетрію: джерелом правди про
контракт є той, хто його виконує та валідує, тобто API.

### 6. Сесії на httpOnly-cookie, Caddy як єдина точка входу

Argon2id для пароля, сесія в httpOnly+Secure cookie, одноразовий токен відновлення
на email з TTL 30 хв, rate-limit на `/auth/*`. Caddy термінує TLS, віддає статику
Angular і проксує `/api` — усе на одному домені.

Причина: JWT у localStorage дає XSS-поверхню без жодної переваги, бо SPA і API
живуть на одному домені — CORS і кросдоменні токени просто не потрібні. Caddy
отримує й оновлює сертифікат Let's Encrypt автоматично, що прибирає ручну роботу
на VPS.

У dev той самий принцип тримає proxy Angular dev-server: `ng serve` проксує `/api`
на контейнер `api`, тож браузер бачить один origin (`localhost:4200`) і cookie
поводиться так само, як у проді. Без цього `localhost:4200` і `localhost:3000` були б
різними origin, і довелося б додавати CORS з `credentials` та `SameSite=None` — код,
потрібний виключно для розробки й нікому не потрібний на проді. Тому `apiBaseUrl`
дорівнює `/api` в обох оточеннях.

### 7. Бекенд без кроку збірки: Node 26 виконує TypeScript напряму

`apps/api` не компілюється. Node 26 стирає типи й виконує `.ts` як є; `tsc`
залишається виключно перевіркою (`--noEmit`). Немає `dist/`, немає watch-компіляції,
Dockerfile копіює вихідники. TypeScript пінується на `6.0.3`.

Причина: збірка бекенду не давала б тут нічого, крім зайвого кроку — ми не бандлимо
код, не мінімізуємо його і не таргетимо старі рантайми. Натомість вона додала б
`dist/`, розсинхрон «зібране відстало від коду», окремий шар у Dockerfile і
watch-процес у dev. Пін TypeScript продиктований Angular: `@angular/compiler-cli@22`
оголошує peer `typescript >=6.0 <6.1`, тоді як latest у реєстрі вже 7.x — без піна
`npm install` падає на peer-конфлікті, і це та помилка, яку легко списати на щось інше.

Це рішення визначило і формат контрактів (див. п. 5): Node не стирає типи всередині
`node_modules`, тому спільний код не може бути workspace-пакетом без компіляції.

### 8. Розробка тільки в контейнерах, без запуску на хості

Жодна команда проєкту не виконується на локальній машині. `docker compose up`
піднімає `postgres`, `api`, `worker` і `web` у watch-режимі; разові команди
(`typecheck`, `lint`, `test`, міграції, генератори Angular) запускаються через
`docker compose run --rm`. Node, npm і Angular CLI на хості не потрібні.

Причина: `sharp` і `argon2` — нативні модулі. Встановлені на macOS, вони не
запустяться в Linux-контейнері, тому `node_modules` живуть в іменованому volume, а
не приїжджають з хоста. Компроміс «залежності ставимо локально, а запускаємо в
контейнері» тут не працює в принципі. Друга причина простіша: оточення одне — те, в
якому розробляєш, і є тим, що їде на прод, тож «у мене працює» перестає бути
можливим діагнозом.

Побічний виграш — версія Node на хості перестає мати значення. Вимога Angular
(`^22.22.3 || ^24.15.0 || >=26.0.0`) стосується лише образу.

- Один `docker compose up` піднімає всю систему; локальне середовище ідентичне проду.
- Домен тестується без інфраструктури — порти підміняються in-memory адаптерами.
- Контейнерів п'ять (`caddy`, `api`, `worker`, `postgres` + разові міграції), бекап —
  один `pg_dump` плюс R2.
- Витрати на AI передбачувані та вимірювані на рівні окремої картки.
- Синхронізація з маркетплейсами додається як ще один модуль, без змін у `products`.

**Ціна рішення**

- Правила залежностей не тримаються самі: потрібен `dependency-cruiser` у CI,
  інакше межі модулів розмиються за кілька тижнів.
- Спільний образ означає спільний реліз: зміна у воркері перезапускає і api.
- pg-boss навантажує ту саму базу, що й застосунок; при зростанні доведеться
  або виносити чергу, або окремий інстанс Postgres.
- Presigned URL з R2 мають TTL — фронт повинен уміти їх оновлювати.
- Розробка в контейнерах повільніша на macOS: bind mount коду через VirtioFS додає
  затримку, а file watching інколи потребує polling. Приймається свідомо заради
  єдиного оточення.
- Відмова від збірки звужує синтаксис: на бекенді недоступні `enum`, `namespace` і
  parameter properties у конструкторах. Обмеження перевіряє `erasableSyntaxOnly`.
- TypeScript не можна оновлювати вільно: версія прив'язана до вимог Angular, тож
  мажорні оновлення фронту й бекенду відбуваються разом.
- Один процес Postgres = єдина точка відмови. Приймається свідомо; страхує
  щоденний бекап.

## Розглянуті альтернативи

| Варіант | Чому відхилено |
|---|---|
| Мікросервіси (окремо media/ai/products) | Мережеві межі та розподілені транзакції коштують дорожче за вигоду при 100 товарах/міс |
| Моноліт одним процесом, без воркера | Розпізнавання на десятки секунд у HTTP-запиті: таймаути проксі, неможливість ретраїв |
| Redis / RabbitMQ для черги | Зайвий контейнер, бекап і точка відмови; Postgres покриває потребу з запасом |
| Next.js / NestJS full-stack замість Angular + Fastify | Стек Angular + Material уже знайомий; SSR і гідратація адмінці не потрібні |
| S3 / зберігання фото на диску VPS | S3 — плата за egress; локальний диск не переживає переїзд VPS і ускладнює бекап |
| Prisma замість SQL-first доступу | Домен має лишатися вільним від ORM-типів; порти легше реалізувати тонким шаром запитів |
| Власний скрапінг Prom/OLX для цін | Крихко, юридично сумнівно, вимагає підтримки парсерів; web search вирішує задачу одним викликом |
| Vercel / керований PaaS замість Hetzner | Довгі AI-задачі й воркери погано лягають на serverless; VPS дешевший і передбачуваніший |
| `tsc`/бандлер для збірки бекенду | Нічого не дає без бандлінгу й мінімізації, але додає `dist/`, watch-процес і клас помилок «зібране відстало» |
| Спільні контракти окремим npm-пакетом | Node не стирає типи в `node_modules` — пакет довелося б компілювати, ставши єдиним build-кроком у проєкті |
