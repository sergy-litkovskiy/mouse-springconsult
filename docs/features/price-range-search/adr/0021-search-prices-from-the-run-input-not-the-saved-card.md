# 0021 — Шукати ціну за входом запуску, а не за збереженою карткою

- **Status:** Accepted
- **Date:** 2026-10-08
- **Deciders:** Serhii (Architect / Tech Lead)

## Context

Сьогодні запуски `price` і `both` будують запит пошуку зі **збережених** полів картки
(`priceQuery(card)` у `PreparationService`, `priceQueryInput` у `PreparationRunService`), а кнопка
ціни у формі вмикається за **чернеткою**. User, який переніс пропозицію стрілкою чи вписав назву й
не зберіг форму, шукав би за старим. AC-03 прямо вимагає, щоб «Згенерувати все» шукало за щойно
підготованими текстами, ще не збереженими. Рішення визначає тіло запиту запуску в `ai.contract.ts`,
payload задачі черги й правило входу, які бачать `api`, `worker` і `web`.

## Decision drivers

- AC-01, AC-02: потрібні хоча б одна назва й хоча б один опис, з будь-якого майданчика.
- AC-03: «Згенерувати все» шукає за щойно підготованими назвою й описом (Prom пріоритетно).
- AC-07: повтор без змін входу — новий пошук, а не старий результат.
- [ADR 0015](../../product-creation-flow/adr/0015-add-per-field-text-rewrite-scope.md): прецедент — `field` несе чернетку в тілі запиту.

## Considered options

1. **Вхід запуску.** `price` несе назви й описи обох майданчиків з чернетки; `both` шукає за
   щойно згенерованими текстами в пам'яті запуску. Збережених полів пошук не читає.
2. **Збережені поля для кнопки.** `price` читає картку, кнопка доступна лише на збереженій формі;
   `both` — за свіжими текстами.

## Decision outcome

**Chosen: опція 1.** Одне правило для обох запусків — «шукаємо те, що user бачить» — і жодного
стану, коли кнопка доступна, а пошук іде за старим текстом.

1. Тіло запиту `{scope: 'price', titleProm, titleOlx, descriptionProm, descriptionOlx}` — рядки з
   чернетки форми.
2. `PreparationRunService` обирає назву (Prom, інакше OLX) і опис (Prom, інакше OLX). Опис
   проходить `draftPlainText` (HTML опису Prom → текст), і обидва рядки обрізаються константою
   `config.ts`. Порожня назва чи опис — `PreparationInputIncomplete` (AC-02). Ключ ідемпотентності
   рахується з обраної пари, і після завершення запуску той самий вхід ставить новий
   (ADR 0017 №6, AC-07).
3. Payload задачі `price` несе обрану пару; `worker` картку для пошуку не читає.
4. Запуск `both` приймається без тексту в тілі. `worker` шукає за `titleProm`/`descriptionProm`, які
   щойно повернув виклик текстів (`titleOlx`/`descriptionOlx`, якщо перші порожні), — у тому самому
   запуску, після текстів.
5. Та сама функція вибору пари живе в `products/preparation` і викликається для обох областей.

## Consequences

**Positive**

- Пошук відповідає тому, що на екрані, незалежно від збереження форми.
- Правило вибору пари — в одному місці бекенду.

**Negative**

- Контракт запуску змінюється: `price` отримує поля тіла, а `web` має їх надсилати.
- Payload черги несе тексти, тож обрізання до константи обов'язкове.

**Neutral**

- `priceQuery(card)` і `priceQueryInput(product)` зникають.
- Передумати на опцію 2 — правка контракту й гейта кнопки, без міграції даних.
