# T143 — Приймання: QG-1–QG-3 на живому стеку й живому магазині

## Context

Прогін якостей з [sad.md §10](../sad.md#10-quality-requirements) на зібраній фічі. Тестової
компанії Prom немає: кожна жива відправка пише в магазин на ~1000 товарів, а ручних імпортів не
більше 10 на добу. Тому живих відправок дві, і запускає їх людина. Класифікатор auto mode блокує
записи в магазин для Claude; читання (статус, товар, список) він дозволяє.

- **Без токена** — стек локально: QG-2 і QG-3 на відмовах, без жодного запису в Prom.
- **З токеном** — дві відправки: картка з усіма фото (сценарій 1) і картка з тимчасово відсутнім
  фото, а потім «Повторити» (сценарій 4). Обидва товари після прийому видаляються в кабінеті.

До релізу ще: підрахунок назв для Prom понад 130 на проді (PRD §8) і запит до `pgboss.job` на
проді, що черга `prom-sync` порожня.

## Sequence

[sad.md §6](../sad.md#6-runtime-view), сценарії 1–4 — те, що перевіряється наскрізно:

> `web-->>user: «Чернетку створено, фото N з N», посилання; published-prom не змінюється`
> `web-->>user: одна чернетка з усіма фото; кнопки більше немає (AC-14)`
> `api-->>web: running — лоадер «Prom ще обробляє картку»`

## Data delta

Що перевіряється в схемі: після сценарію 1 — `products.prom_id` записано, у
`product_prom_sync_runs` один рядок `succeeded` з `images_on_prom` = `images_total`. Після сценарію
4 — два рядки: `failed` `prom_photos_incomplete` і `succeeded`, `prom_product_id` однаковий.
Після відмов `products` не змінено. Колонки `products.category` немає.

## API contract excerpt

```yaml
    PromSyncStatus:
      enum: [queued, running, succeeded, failed]
        `product_prom_sync_runs.status` CHECK — той самий перелік, що в підготовки. `succeeded`
        означає одне: чернетка, фото N з N, `promId` картки записано. Частковий результат — це
```

## Acceptance criteria

Quality goals з [sad.md §10](../sad.md#10-quality-requirements):

**QG-1** — недоторканність живого магазину
**Given** знімок каталогу магазину до відправки
**When** проходять обидві живі відправки, зокрема повтор
**Then** знімок після відрізняється лише двома тестовими товарами; `not_in_file` = 0 у кожному звіті в лозі `worker`

**QG-2** — чесний і відновлюваний стан
**Given** стек без токена, а потім частковий результат на живому магазині
**When** user відправляє картку й повторює
**Then** відмова закривається `prom_access_denied` без зміни картки; повтор дає одну чернетку з усіма фото, у кабінеті один товар

**QG-3** — незаблокований інтерфейс
**Given** готова картка
**When** user натискає «Синхронізувати з Prom» 20 разів на різних картках без токена
**Then** запит ≤ 500 ms за pino-логом, задача стартує ≤ 5 с від постановки

## Checklist

1. Без токена: QG-3 (20 стартів), QG-2 (`prom_access_denied`, поля картки цілі, «Повторити» доступна), друга вкладка під час активної відправки отримує ту саму (AC-13).
2. Межі: назва 130/131, слово 50/51, ключові слова 1024/1025 — кнопка й `409 prom_sync_not_ready` (PRD §6).
3. Скрипт фаз для людини: знімок каталогу; сценарій 1; сценарій 4 з відсутнім фото й «Повторити»; знімок після. Людина запускає записи через `! bash …`, Claude читає лог.
4. Перевірити картку: «Чернетку створено, фото N з N», посилання на кабінет веде на товар, published-prom не змінено (AC-15), кнопки немає (AC-14).
5. Те, що контрольна відправка не перевірила: у сценарії 1 ціна на Prom дорівнює ціні картки до копійок (комірка `Ціна` — рядок); у сценарії 4 між повтором і «довершити» товар «немає в наявності», а назва й опис на Prom не змінились (`presence` в `updated_fields`).
6. Видалити обидва тестові товари в кабінеті; тестові дані прибрати з R2.
7. Перед деплоєм: `char_length(title_prom) > 130` на проді; `pgboss.job` черги `prom-sync` порожня.
