# 0030 — Упізнавати товар на Prom за зовнішнім ідентифікатором, рівним id картки

- **Status:** Accepted
- **Date:** 2026-10-10
- **Deciders:** Serhii (Architect / Tech Lead)

## Context

Імпорт Prom працює з усім каталогом магазину, а не з одним товаром: хибний параметр може приховати
чи видалити ~560 живих товарів (idea-brief §10). Звіт імпорту дає лічильники, а не id створених
товарів, і між «Prom створив товар» та «адмінка це записала» може статися збій — після нього повтор
не має права створити другий товар. Ідентифікатор, яким ми позначимо товар, осяде в живому
магазині, і забрати його звідти буде неможливо.

## Decision drivers

- §1 QG-1 «Недоторканність живого магазину»; AC-03; PRD §6 «0 змінених, прихованих чи видалених
  товарів, крім відправленого».
- §1 QG-2; AC-11, AC-13; PRD §7 KPI «0 дублів».
- Пробний імпорт 2026-10-10: у 996 живих товарів власного зовнішнього ідентифікатора немає, і
  `mark_missing_product_as: none` не змінив жодного з них.
- PRD §6.1, abuse case «Запис у живий магазин».

## Considered options

1. **Зовнішній ідентифікатор = id картки** — у файл імпорту йде uuid картки; перед подачею відправка
   шукає товар за ним і подає імпорт лише тоді, коли товару ще немає.
2. **Id товару зі звіту імпорту** — зовнішнього ідентифікатора не ставимо, запам'ятовуємо id
   створеного товару й повторюємо роботу з ним.

## Decision outcome

**Chosen: зовнішній ідентифікатор = id картки.** Лише він дає знайти «свій» товар після будь-якого
збою: звіт імпорту id товарів не повертає, тож варіант 2 мусив би шукати товар за назвою чи часом
створення, і збій між імпортом і записом давав би дубль. Імпорт удруге не подається, коли товар уже
є, — окрім повтору для фото (K < N, AC-12): тоді файл картки подається ще раз, і Prom оновлює саме
цей товар за зовнішнім id. Поруч закріплено захист каталогу: параметри імпорту — дві константи
адаптера без аргументів, обидві з `mark_missing_product_as: none`. Перша подача йде з параметрами за
замовчуванням. Повтор для фото йде з `force_update: true` і `updated_fields: ["images_urls",
"presence"]`, бо без `force_update` Prom незмінений файл пропускає (`not_changed`). Контрольна
відправка 2026-10-10 перевірила `["images_urls"]`; `presence` додано після неї, і живцем його
перевіряє приймання (sad.md §11). Лічильник «не у
файлі» звіряється з 0, решта лічильників пишеться в лог на кожній відправці.

## Consequences

**Positive**

- Повтор після будь-якого збою знаходить той самий товар; дубль можливий лише тоді, коли Prom сам
  ігнорує зовнішній ідентифікатор.
- Подати імпорт з параметром, що чіпає інші товари, неможливо без зміни коду адаптера й рев'ю.
- Відхилення лічильників звіту видно в логах `worker` на кожній відправці (PRD §6).

**Negative**

- Повтор для фото (AC-12) повертає товар з чернетки на вітрину: після імпорту Prom публікує все,
  що імпортував. Тому «довершити» після повтору знову ставить чернетку, а `presence` у повторі
  тримає товар «немає в наявності», доки чернетки немає. Уже скачані фото Prom лишає й не дублює
  (контрольна відправка 2026-10-10, протокол — `api-sync-report.md`).
- Лічильник, що показує зміну чужого товару, вже нічого не відкотить: перевірка виявляє, а не
  запобігає. Запобігає лише константа параметра.

**Neutral**

- Uuid картки в кабінеті Prom видно як код чи зовнішній ідентифікатор товару — службове поле,
  покупцям його не показують.
- Змінити схему ідентифікації пізніше означає жити з двома схемами: товари, вже створені з uuid,
  його збережуть.
