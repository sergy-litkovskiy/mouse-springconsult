# 0004 — Приймати кадри через API і перевіряти їх до запису в R2

- **Status:** Accepted
- **Date:** 2026-09-01
- **Deciders:** Serhii (Architect / Tech Lead)

## Context

Ця поставка вперше вводить у систему зовнішнє файлове сховище (Cloudflare R2 за S3-API) — межу, якої в проєкті не було, і саме через неї PRD §6.1 позначає security review як обовʼязковий. Кадр приходить з браузера й має потрапити в R2; питання в тому, чи проходить він при цьому через наш HTTP-процес. PRD §6.1 прямо вимагає перевірки, що файл справді є зображенням, **до** потрапляння у сховище, і межі розміру ≤ 10 МБ (PRD §6). Рішення визначає форму ендпоінта завантаження, налаштування Caddy й Fastify, потребу в CORS на бакеті та стрілки на діаграмах §3 і §5.

## Decision drivers

- PRD §6.1: «Небезпечний файл на вході: межа розміру (§6) і перевірка, що це справді зображення, до потрапляння у сховище».
- PRD §6.1: «публічного переліку вмісту сховища немає» — жоден сторонній не має отримувати право запису в бакет.
- §1 QG-2 «Незаблокований інтерфейс»: превʼю ≤ 1 с, форма не блокується — шлях завантаження не повинен тримати користувача.
- §2 Constraints: обсяг 50-100 товарів на місяць і один-два адміни — пропускна здатність контейнера `api` не є вузьким місцем.
- `ARCHITECTURE.md`: «Зображення ніколи не проксуються через API — тільки R2 і presigned URL» — обмеження стосується **читання**, і рішення не має його порушувати.

## Considered options

1. **Через API** — браузер шле multipart-форму на наш ендпоінт; контролер тримає межу розміру (разом із `bodyLimit` Fastify і лімітом Caddy), а справжній тип за сигнатурою вмісту перевіряє `MediaService` — єдиний, хто пише в R2, тож жоден шлях до сховища не може обійти перевірку (SAD §5). Лише після цього байти йдуть у R2.
2. **Напряму в R2 за presigned PUT** — API видає одноразове підписане посилання на запис, браузер вантажить файл у сховище повз наш сервер, потім повідомляє API, що готово.

## Decision outcome

**Chosen: опція 1 — через API.** Вимога PRD §6.1 сформульована як «до потрапляння у сховище», і лише перший варіант виконує її буквально: при presigned PUT файл фізично опиняється в R2 раніше, ніж система дізнається про його існування, тож перевірка перетворюється на прибирання вже записаного сміття. Другий драйвер — обсяг: при 50-100 кадрах на місяць економія трафіку контейнера `api` не купує нічого, а коштує налаштування CORS на бакеті, права запису у зовнішнього клієнта й окремого прибиральника обʼєктів, про які браузер так і не дозвітував.

## Consequences

**Positive**

- Вимога PRD §6.1 виконується буквально: у сховищі ніколи немає неперевіреного обʼєкта.
- Право запису в бакет лишається тільки в бекенда; браузер туди лише читає, і робить це за постійною адресою, виведеною з ключа ([ADR 0007](0007-serve-images-from-a-public-bucket.md)).
- CORS на бакеті R2 не потрібен зовсім, бо браузер туди не пише.
- Немає стану «обʼєкт у сховищі є, а рядка в БД немає» — джерело сирітських файлів зникає разом зі шляхом, який їх породжував.

**Negative**

- Тіло до 10 МБ проходить через Caddy і через контейнер `api`: обидва потребують піднятого ліміту розміру тіла запиту, і це треба не забути в `infra/caddy/Caddyfile` і в конфігурації Fastify.
- Пропускна здатність завантаження обмежена каналом VPS, а не каналом R2. При нинішньому обсязі це не має значення, але межа існує.

**Neutral**

- Перехід на presigned PUT пізніше можливий і не потребує міграції даних: ключі обʼєктів і форма запису в `product_images` від шляху завантаження не залежать. Ціна переходу — новий ендпоінт видачі посилання, CORS на бакеті й прибиральник сиріт.
- Рішення стосується лише **запису**. Читання лишається прямим — браузер бере кадр з R2 сам, повз `api`, — але за постійною публічною адресою, а не за підписаним посиланням: це вирішує [ADR 0007](0007-serve-images-from-a-public-bucket.md). Рядок `ARCHITECTURE.md` про presigned URL цим перекрито (SAD §11).
