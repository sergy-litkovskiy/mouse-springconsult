# T51 — Повтор підготовки після відмови

## Context

Знайдено 2026-09-19 під час RED T29. Ключ ідемпотентності (картка, область, версія входу) має
UNIQUE на всю таблицю `product_preparation_runs`. Тому запуск, що завершився `failed`
(`preparation_failed` чи `price_unavailable`), займає свій ключ назавжди. Коли `user`
повторює запуск з тим самим входом, маршрут T29 повертає той самий відмовлений запуск (`200`)
і задачі не ставить. Повторити підготовку неможливо, поки людина не змінить фото, заголовок чи
опис.

Це суперечить AC-10: система «лишає картку придатною для повторного запуску, … повторний
запуск — дія user-а». І AC-10b: «ціну можна запросити окремо» — після `price_unavailable`
у запуску `price` другий такий самий запит ціни теж повертає відмову.

Ідемпотентність потрібна проти подвійної оплати **того самого** результату: подвійного кліку
чи повтору запиту, поки запуск іде або вже вдався. Відмовлений запуск результату не має, тож
захищати нема чого.

## Sequence

[sad.md §6](../sad.md#6-runtime-view), сценарій 7: повторний `POST` з тим самим входом після
`failed` ставить нову задачу, як перший запуск.

## Data delta

| Що | Зміна |
|---|---|
| `product_preparation_runs_idempotency_key_key` | UNIQUE на всю таблицю → частковий UNIQUE `WHERE status <> 'failed'` (нова міграція, T26 не редагується) |
| рядки | відмовлений запуск лишається в історії; новий запуск того самого входу — новий рядок |

Варіант на старті перевірити: частковий індекс проти окремої колонки-лічильника спроб у ключі.
Частковий індекс простіший і тримає інваріант у БД, а не в коді.

## API contract excerpt

```yaml
        UNIQUE у `product_preparation_runs`; повторний виклик з тим самим входом
        повертає наявний запуск (`200`), а не створює новий (`201`). "Версія входу" —
```

Опис треба доповнити: «наявний» означає лише незавершений (`queued`/`running`) чи
`succeeded`. Після `failed` той самий вхід дає `201`.

## Acceptance criteria

**AC-37** (US-03, US-04) — повтор після відмови
**Given** запуск картки завершився `failed` з будь-яким `error_code`
**When** `user` запускає ту саму область з тим самим входом
**Then** система ставить нову задачу й відповідає `201` з новим запуском. Відмовлений
запуск лишається в історії, і його токени входять у вартість картки (AC-14)

**AC-38** — ідемпотентність не слабшає
**Given** запуск з тим самим входом `queued`, `running` чи `succeeded`
**When** `user` запускає ту саму область ще раз
**Then** система повертає наявний запуск (`200`) і задачі не ставить

## Checklist

1. Міграція: зняти UNIQUE, створити частковий UNIQUE `WHERE status <> 'failed'`. Down
   повертає повний UNIQUE; down на базі з двома рядками одного ключа має падати явно.
2. `PreparationRepository.createRunOnce` — `ON CONFLICT` проти часткового індексу, а
   перечитування наявного запуску — лише серед не-`failed`.
3. `openapi.yaml` (опис `startPreparationRun`), `data-model.md` (індекс), `events.md`.
