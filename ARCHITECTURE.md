# ARCHITECTURE

## Патерн

**Модульний моноліт з портами й адаптерами, розгорнутий у кількох контейнерах.**

Одна кодова база (`apps/api`), один Docker-образ, різні точки входу. Бізнес-логіка
розділена на вертикальні модулі за фічами; шари всередині модуля позначені суфіксами
файлів, а не вкладеними каталогами. Інфраструктура (БД, R2, черга, пошта, AI) захована
за портами й реалізована адаптерами, які підключаються тільки в composition root.

Бекенд **не має кроку збірки**: Node 26 стирає типи й виконує `.ts` напряму, тож
`tsc` потрібен лише для перевірки (`--noEmit`). У проєкті немає `dist/`, немає
розсинхрону «зібране відстало від коду», а Dockerfile зводиться до копіювання
вихідників. Ціна — синтаксис має бути стираним (без `enum`, `namespace` і parameter
properties) і TypeScript пінується на 6.0.3, бо Angular 22 вимагає `>=6.0 <6.1`.

## Розгортання

```
                    Internet :443
                         │
                   ┌─────▼─────┐
                   │   caddy   │  TLS (Let's Encrypt), статика Angular,
                   └──┬─────┬──┘  reverse proxy /api → api:3000
                      │     │
          /*  ────────┘     └──────── /api/*
      (dist Angular)              ┌────▼────┐
                                  │   api   │  Fastify: HTTP, auth, CRUD,
                                  └────┬────┘  ставить задачі в чергу
                                       │
                                  ┌────▼──────┐         ┌──────────────┐
                                  │ postgres  │◄────────┤    worker    │
                                  │ дані+черга│  pg-boss│ sharp → R2   │
                                  └───────────┘         │ Claude API   │
                                                        │ web search   │
                                                        └──────┬───────┘
                                                               │
                                        Cloudflare R2 ◄────────┘
                                        Anthropic API ◄────────┘
```

`api` і `worker` — той самий образ із різною командою запуску (`src/api.ts`
і `src/worker.ts`). Це «кілька контейнерів», а не «кілька сервісів»: спільні
типи, спільні міграції, один реліз.

## Модулі

| Модуль | Відповідальність |
|---|---|
| `auth` | Вхід адміна, сесії, відновлення пароля через email |
| `products` | Картка товару: тексти, ціна, статус `draft/ready/sold`, м'яке видалення |
| `media` | Прийом файлів, sharp-конвеєр, похідні розміри, R2, порядок галереї |
| `ai` | Розпізнавання за фото, генерація опису й SEO, пошук ринкових цін, облік `usage` |

Модуль — це **одна папка**. Шари всередині виражені суфіксами файлів
(`*.routes.ts`, `*.use-case.ts`, `*.port.ts`, `*.repository.ts`, `*.adapter.ts`),
а не вкладеними каталогами: при десятку файлів вкладеність лише додає кліків.
Розкладаємо модуль на підпапки тоді, коли він справді виросте.

Пошук цін не виділено в окремий модуль: це той самий Claude, лише інший use-case
всередині `ai`. Синхронізація з Prom/OLX стане модулем `marketplace`, коли до неї
дійде черга, — до того порожньої папки під неї не існує.

Технічні сервіси без бізнес-змісту — конфіг, пул Postgres, логер, черга, базовий
клас помилки — лежать окремими файлами прямо в `src/`, поруч з точками входу. Вони
не знають, що існують товари. Окремого каталогу-шару під них немає: п'ять файлів
його не окупають.

R2-клієнт і SMTP свідомо туди не потрапили — це адаптери портів `ImageStorage` і
`Mailer`, які оголошують `media` та `auth`, тож живуть усередині своїх модулів.

## Dependency rule

Залежності спрямовані **всередину**. Стрілка назовні — помилка архітектури, а не
стильова дрібниця.

```
   src/api.ts · src/worker.ts   (composition root — тут і тільки тут усе склеюється)
             │
             ▼
  ┌───────────────────────────────────────────────────┐
  │  modules/<feature>/                               │
  │                                                   │
  │   *.routes.ts ──► *.use-case.ts ──► *.port.ts     │
  │                                     доменні типи  │
  │                                          ▲        │
  │            *.repository.ts / *.adapter.ts ┘       │
  │                     реалізують порти              │
  └───────────────────────┬───────────────────────────┘
                          ▼
    src/config.ts · db.ts · logger.ts · queue.ts · errors.ts
```

1. **Технічні сервіси не залежать від `modules`.** `config.ts`, `db.ts`, `logger.ts`,
   `queue.ts`, `errors.ts` не знають, що існують товари. Доменні помилки оголошує той
   модуль, якому вони належать; у `src/errors.ts` лише базовий `AppError`.
2. **Модуль бачить інший модуль лише через `index.ts`.** Deep import заборонено;
   циклів між модулями немає. Шини подій поки немає — при чотирьох модулях прямий
   виклик public API простіший і трасується стектрейсом.
3. **Порти й доменні типи не мають I/O.** Жодних `pg`, `fastify`, `@aws-sdk`,
   `@anthropic-ai/sdk`. Модуль оголошує порти (`ProductRepository`, `ImageStorage`,
   `ProductRecognizer`, `PriceResearcher`, `Mailer`), реалізації живуть у файлах
   `*.repository.ts` / `*.adapter.ts`.
4. **Use-case залежить від порту, не від реалізації.** Імпорт `*.repository.ts`
   з `*.use-case.ts` — помилка; підміна Postgres на in-memory у тестах не повинна
   торкатися бізнес-логіки.
5. **Реалізації інстанціює тільки composition root** — `src/api.ts` і `src/worker.ts`.
6. **`src/contracts/` не залежить ні від чого** — чисті zod-схеми без I/O. Джерелом
   правди є бекенд: він приймає й валідує запити, тому контракти живуть у ньому, а
   фронт підключає їх через alias `@contracts/*`. Окремого npm-пакета немає свідомо:
   він вимагав би компіляції в JS (Node не стрипає типи всередині `node_modules`) і
   став би єдиним build-кроком у проєкті, який інакше обходиться без збірки.

Фронтенд тримається [style guide Angular](https://angular.dev/style-guide): групування
за фічею, без каталогів `core/`, `shared/` і без папок за типом коду (`services/`,
`components/`, `ui/`). Фічі не імпортують одна одну; спільне піднімається на рівень
`app/` під конкретним іменем. Типи — з `@contracts`.

Правила перевіряються `docker compose run --rm api npm run deps:check`
(dependency-cruiser по glob-ах імен файлів для api, ESLint-межі для web) і є частиною
CI — порушення валить збірку.

## Потік «фото → картка»

1. `POST /api/products` з першим фото → `media` кладе оригінал у R2, `products`
   створює `draft`, `api` ставить задачу `product.recognize` у pg-boss і одразу
   повертає `productId` + `jobId`.
2. `worker` бере задачу: sharp зменшує кадр до ≤ 1568 px / JPEG q80 (економія
   токенів), `ai` викликає `claude-opus-5` зі structured outputs і отримує plain-text
   поля, і другим use-case через `web_search_20260209` знаходить діапазон цін по Україні.
3. Результат пишеться в `products` + `ai_generations` (з `usage`), стан задачі
   оновлюється; UI бачить готову картку через polling статусу.
4. Додаткові фото йдуть коротким шляхом: sharp → R2 → рядок у `product_images`,
   **без** AI. Видалення прибирає і рядок, і обʼєкт у R2.

## Межі, які тримаємо свідомо

- Черга — у Postgres. Redis з'явиться лише тоді, коли навантаження це доведе.
- Зображення ніколи не проксуються через API — тільки R2 і presigned URL.
- Виклики AI бувають **тільки** у воркері. HTTP-процес не чекає на зовнішній API.
- Порожніх модулів «про запас» не тримаємо: `marketplace` з'явиться разом з першим
  файлом інтеграції, і `products` при цьому переробляти не доведеться.
- Бекенд не збирається. Якщо колись знадобиться бандлити його в один файл — це буде
  свідоме рішення з власним ADR, а не побічний ефект доданого інструмента.
