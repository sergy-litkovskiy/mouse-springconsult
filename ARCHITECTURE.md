# ARCHITECTURE

## Патерн

**Модульний моноліт із класичною тришаровою схемою, розгорнутий у кількох контейнерах.**

Одна кодова база (`apps/api`), один Docker-образ, різні точки входу. Бізнес-логіка
розділена на вертикальні модулі за фічами; шари всередині модуля — `Controller →
Service → Repository → Entity` — позначені суфіксом імені класу, а не вкладеними
каталогами. Залежності передаються конструктором і склеюються в composition root.

Бекенд **збирається** `tsc` у `dist/`, звідки Node його й запускає. Причина одна:
entity описані декораторами `@Entity`/`@Column`, а Node декоратори не трансформує —
лише стирає типи ([ADR 0003](docs/adr/0003-three-layer-classes.md)). Ціна — крок
збірки в Dockerfile і в CI; виграш — TypeORM у своєму звичному вигляді, parameter
properties у конструкторах і жодного окремого шару портів. TypeScript пінується на
6.0.3, бо Angular 22 вимагає `>=6.0 <6.1`.

## Розгортання

```
                    Internet :443
                         │
                   ┌─────▼─────┐
                   │   caddy   │  TLS (Let's Encrypt), статика Angular,
                   └──┬─────┬──┘  reverse proxy /api → api:3000
                      │     │
          /*  ────────┘     └──────── /api/*
      (dist Angular)              ┌────▼────┐
                                  │   api   │  Fastify: HTTP, auth, CRUD,
                                  └────┬────┘  ставить задачі в чергу
                                       │
                                  ┌────▼──────┐         ┌──────────────┐
                                  │ postgres  │◄────────┤    worker    │
                                  │ дані+черга│  pg-boss│ sharp → R2   │
                                  └───────────┘         │ Claude API   │
                                                        │ web search   │
                                                        └──────┬───────┘
                                                               │
                                        Cloudflare R2 ◄────────┘
                                        Anthropic API ◄────────┘
```

`api` і `worker` — той самий образ із різною командою запуску (`src/api.ts`
і `src/worker.ts`). Це «кілька контейнерів», а не «кілька сервісів»: спільні
типи, спільні міграції, один реліз.

## Модулі

| Модуль | Відповідальність | Стан |
|---|---|---|
| `auth` | Вхід адміна, сесії, відновлення пароля через email | вхід/вихід/перевірка сесії реалізовані ([ADR 0002](docs/adr/0002-auth-jwt-and-typeorm.md)); відновлення пароля — попереду |
| `products` | Картка товару: окремі тексти для Prom і OLX, ціна, категорія, стан речі, публікація, галерея | каталог з пагінацією, фільтрами і сортуванням реалізований; створення й редагування — попереду |
| `media` | Прийом файлів, sharp-конвеєр, похідні розміри, R2, порядок галереї | попереду |
| `ai` | Розпізнавання за фото, генерація опису й SEO, пошук ринкових цін, облік `usage` | попереду |

Модуль — це **одна папка**. Шари всередині виражені суфіксом імені класу
(`ProductController`, `ProductService`, `ProductRepository`), а не вкладеними
каталогами: при десятку файлів вкладеність лише додає кліків. Entity-клас суфікса не
має, бо він і є моделлю: `Product` — і доменний обʼєкт, і ORM-мапінг.
Розкладаємо модуль на підпапки тоді, коли він справді виросте.

Пошук цін не виділено в окремий модуль: це той самий Claude, лише інший метод сервісу
всередині `ai`. Синхронізація з Prom/OLX стане модулем `marketplace`, коли до неї
дійде черга, — до того порожньої папки під неї не існує.

Технічні сервіси без бізнес-змісту — конфіг, пул Postgres, логер, черга, базовий
клас помилки — лежать окремими файлами прямо в `src/`, поруч з точками входу. Вони
не знають, що існують товари. Окремого каталогу-шару під них немає: п'ять файлів
його не окупають.

R2-клієнт і SMTP свідомо туди не потрапили — це `ImageStorage` і `Mailer` модулів
`media` та `auth`, тож живуть усередині своїх модулів, поруч із сервісами, які їх
викликають.

## Dependency rule

Залежності спрямовані **всередину**. Стрілка назовні — помилка архітектури, а не
стильова дрібниця.

```
 src/api.ts · src/worker.ts · db/*.ts   (composition root — тут і тільки тут усе склеюється)
             │
             ▼
  ┌────────────────────────────────────────────────────────┐
  │  modules/<feature>/                                    │
  │                                                        │
  │   *Controller.ts ──► *Service.ts ──► *Repository.ts    │
  │      HTTP, zod, DTO   бізнес-логіка   ──► Entity       │
  │                                           typeorm · pg │
  └───────────────────────┬────────────────────────────────┘
                          ▼
    src/config.ts · db.ts · logger.ts · queue.ts · errors.ts
```

1. **Технічні сервіси не залежать від `modules`.** `config.ts`, `db.ts`, `logger.ts`,
   `queue.ts`, `errors.ts` не знають, що існують товари. Доменні помилки оголошує той
   модуль, якому вони належать; у `src/errors.ts` лише базовий `AppError`.
2. **Модуль бачить інший модуль лише через `index.ts`.** Deep import заборонено;
   циклів між модулями немає. Шини подій поки немає — при чотирьох модулях прямий
   виклик public API простіший і трасується стектрейсом.
3. **ORM живе в репозиторіях і entity-класах.** `typeorm` і `pg` не з'являються ні в
   сервісі, ні в контролері: сервіс, який будує QueryBuilder, поглинув шар під собою.
   Решта інфраструктури — argon2, jose, R2, Anthropic — теж належить конкретному класу
   свого модуля (`PasswordHasher`, `SessionTokens`, `ImageStorage`), а не спільній теці.
4. **Контролер ходить через сервіс.** Імпорт `*Repository.ts` з `*Controller.ts` —
   помилка: бізнес-логіка не повинна бути досяжною повз шар, якому вона належить.
   Контролер відповідає за валідацію запиту, авторизацію, куки і мапінг у DTO —
   і більше ні за що.
5. **Класи створює тільки composition root** — `src/api.ts`, `src/worker.ts` і скрипти
   в `db/` (процес міграцій); залежності передаються конструктором. Виняток:
   `*.spec.ts` створює клас напряму, а двійники описує підкласами з `override`.
6. **`src/contracts/` не залежить ні від чого** — zod-схеми без I/O (`*.contract.ts`)
   і константи контракту зовсім без залежностей (`error-codes.ts`, `auth-limits.ts`).
   Фронт бере зі схем лише типи, а в рантаймі імпортує другі: інакше zod поїхав би
   у бандл браузера. Джерелом
   правди є бекенд: він приймає й валідує запити, тому контракти живуть у ньому, а
   фронт підключає їх через alias `@contracts/*`. Окремого npm-пакета немає свідомо:
   він вимагав би власного циклу «зібрав — опублікував — оновив версію» заради файлів,
   які обидва застосунки й так читають з диска.

Фронтенд тримається [style guide Angular](https://angular.dev/style-guide): групування
за фічею, без каталогів `core/`, `shared/` і без папок за типом коду (`services/`,
`components/`, `ui/`). Фічі не імпортують одна одну; спільне піднімається на рівень
`app/` під конкретним іменем. Типи — з `@contracts`.

Правила перевіряються двома командами, окремо на застосунок (`node_modules` у
контейнерів різні): `api npm run deps:check` — dependency-cruiser по glob-ах імен
класів, `web npm run lint` — ESLint-межі між фічами. Обидві є частиною CI —
порушення валить збірку.

## Потік «фото → картка»

1. `POST /api/products` з першим фото → `media` кладе оригінал у R2, `products`
   створює неопубліковану картку, `api` ставить задачу `product.recognize` у pg-boss і одразу
   повертає `productId` + `jobId`.
2. `worker` бере задачу: sharp зменшує кадр до ≤ 1568 px / JPEG q80 (економія
   токенів), `ai` викликає `claude-opus-5` зі structured outputs і отримує plain-text
   поля, і другим викликом через `web_search_20260209` знаходить діапазон цін по Україні.
3. Результат пишеться в `products` + `ai_generations` (з `usage`), стан задачі
   оновлюється; UI бачить готову картку через polling статусу.
4. Додаткові фото йдуть коротким шляхом: sharp → R2 → рядок у `product_images`,
   **без** AI. Видалення прибирає і рядок, і обʼєкт у R2.

## Межі, які тримаємо свідомо

- Черга — у Postgres. Redis з'явиться лише тоді, коли навантаження це доведе.
- Зображення ніколи не проксуються через API — тільки R2 і presigned URL.
- Виклики AI бувають **тільки** у воркері. HTTP-процес не чекає на зовнішній API.
- Каркас із чотирьох модулів закріплений у git; п'ятого «про запас» не заводимо:
  `marketplace` з'явиться разом з першим файлом інтеграції, і `products` при цьому
  переробляти не доведеться.
- Збірка бекенду — це `tsc` і більше нічого. Бандлер, мініфікація чи one-file build
  будуть свідомим рішенням з власним ADR, а не побічним ефектом доданого інструмента.
