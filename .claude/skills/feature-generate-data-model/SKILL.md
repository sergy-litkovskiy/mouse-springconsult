# Skill: feature-generate-data-model

Stage 08+09 runner for the persistence cut in **mouse-springconsult**: schema design +
migration, in one pass, against this repo's actual stack — PostgreSQL 18 + TypeORM, not
a generic SQL-migration tool. Mode (greenfield vs. brownfield) is decided **per entity**,
not per feature: a real feature here typically touches an existing aggregate (brownfield)
while introducing a new one for a later delivery (greenfield-but-deferred). See "Migration
write policy" below — this skill does not always write every migration it designs.

## Owner

Backend Lead (in this project: whoever runs the skill — one operator, no separate roles).

## Boundary with `feature-scaffold`

If a `feature-scaffold`-style skill is also in play for this repo: **this skill designs,
scaffold builds.** `feature-generate-data-model` locks the schema in `data-model.md` and
writes migrations for (a) changes to tables that already exist, and (b) new tables whose
delivery is starting now. A new table that belongs to a clearly later delivery slice is
designed here in full (columns, constraints, indexes) but its migration and entity class
are left for whoever scaffolds that slice — see "Migration write policy".

## When to use

- "data model for `<slug>`", "schema for `<feature>`", "generate migration for `<slug>`",
  "схема для `<slug>`".
- After PRD (stage 03) and sad.md (stage 04-05) are closed.
- `/feature-generate-data-model <slug>` — explicit invocation.
- `/feature-generate-data-model <slug> --drift-only` — just compare entity classes
  against the migrations that created their tables; no generation.
- Skip if `data-model.md` exists AND every entity in it that's in scope for the current
  delivery already has a migration under `apps/api/db/migrations/`.

## Inputs

- `<slug>` — same as for PRD / SAD.
- **Gate (hard refuse if missing):**
  - `docs/features/<slug>/PRD.md` — §4 User stories (entity/aggregate candidates), §5
    Acceptance criteria (bounds: `maxLength`, allowed values, numeric formats).
  - `docs/features/<slug>/sad.md` — §4 Solution strategy (storage-shape decisions — this
    repo's arc42 SAD has no dedicated ER section; look here for statements like "values
    live in their own table" or "no `deleted_at`"), §5 Building block view (which
    files/modules are new vs. changed — this names the aggregate roots), §6 Runtime view
    (sequence diagrams **inline in the document**, not in a separate `diagrams/` folder —
    a `Note over api, pg` or an arrow into `pg` naming a table/column is a query, and a
    query is the only valid reason for an index).
  - Existing schema: `apps/api/db/migrations/*.ts` and `apps/api/src/modules/*/*.ts`
    entity classes — source of truth for what already exists (brownfield delta) and for
    the PII/tone conventions to keep matching.
  - Optional: `apps/api/src/contracts/*-limits.ts` — reuse existing bound constants
    (`productConstraints.titleMaxLength` etc.) instead of re-deriving them from prose.

## Defaults — this repo's actual conventions, not generic SQL-migration defaults

A version of this skill written for another stack (Go + golang-migrate) shipped with
opinions that do not hold here — a prior run already found and documented every one of
these deviations in its audit report. They're folded in below instead of being
rediscovered every time.

| Topic | Default in mouse-springconsult | Why |
|---|---|---|
| Migration format | **One** `MigrationInterface` class per change, `up`/`down` methods in a single `.ts` file | TypeORM's own contract. No `.up.sql`/`.down.sql` pair. |
| Filename / class name | `<epoch-ms>-<kebab-name>.ts`, class `PascalCase<epoch-ms>` — generated by `db:migrate:new -- <kebab-name>`, never hand-typed | TypeORM orders migrations by the timestamp at the **end of the class name**; it leads the file name too, so `ls` shows the same order. |
| Location | `apps/api/db/migrations/` | The only migrations directory in the repo. |
| Discovery | A glob (`db/migrations-glob.ts`) picks up the compiled directory whole | No hand-kept list to update — a new migration takes effect the moment it compiles. If `apps/api/db/migrations-list.ts` still exists when you read this, the repo hasn't caught up to its own migration yet; don't reintroduce it. |
| `IF NOT EXISTS` / idempotent DDL | Not needed | TypeORM tracks applied migrations in its own `migrations` table — a migration cannot run twice by construction. |
| PK | `uuid primary key default uuidv7()`, generated **by Postgres 18**, not by the app | Time-ordered inserts without a sequence; no extension or app-side library needed — `uuidv7()` is native to Postgres 18. |
| Timestamps | `created_at timestamptz not null default now()` on every table that has one meaningful "when". `updated_at` only on entities that are edited in place as a whole (`products` has it); an event-shaped table names its moments precisely instead (`started_at`, `finished_at`, `resolved_at`) rather than adding a generic `updated_at`. | Demonstrated in the applied schema — this is not "immutable-first, no `updated_at` ever"; it's "name the timestamp for what it actually means." |
| Naming | `plural snake_case` tables, `snake_case` columns, every identifier double-quoted in SQL | Applied schema. |
| `CHECK` constraints | **Allowed** for closed value lists and simple numeric bounds (`condition in ('new','used')`, `price >= 0`, `position >= 0`) | This isn't business logic — it's a bound on a single row's own value, and the database is already the thing responsible for row integrity. `TRIGGER` and stored procedures stay out: those encode *behavior*, not a bound. |
| Relations | **No `@OneToMany` / `@ManyToOne`.** A foreign key is a plain `uuid` column (`ProductImage.productId`); the repository joins by hand with a second query. | A relation decorator combined with `LIMIT` makes the page size mean rows, not aggregate roots — see the doc comment on `Product.images`. |
| Lookup tables | Avoided for closed, code-owned enumerations (status/type/scope-style columns) — a TS union + `CHECK` instead of a separate table | `condition` today; the data-model doc for product-creation-flow explicitly kept `scope`/`status`/`field` as code constants rather than rows. Reach for a real table only when the values are genuinely data the app manages (counts change, admin edits them, etc.). |
| `JSONB` | Only for a payload whose *shape* depends on another column's value | `product_field_suggestions.value` — the only JSONB in the schema, with a one-line justification in `data-model.md`. |
| Money | `numeric(12,2)` (`decimal(12,2)` — same type), carried as the decimal string the driver returns, no `transformer` anywhere | `CLAUDE.md` "Гроші". |
| Delete | Hard delete + `on delete cascade` inside one aggregate; no `deleted_at` | A soft-delete predicate would have to enter every catalogue query and every unique index — not worth it at this scale, and a soft-deleted card without photos isn't "ready" anyway. |
| Computed state | Never store what a read can derive (readiness, totals) | ADR 0009 in product-creation-flow. |
| Breaking change (rename/drop/retype) | One migration, if there's nothing to move on live rows. Reach for the 3-phase expand → backfill → contract dance only when a real backfill of existing data is involved. | 50-100 rows/month, one-two admins — a maintenance window is not a constraint here the way it is at scale. |
| Test fixtures | Local `seedX()` helper functions declared at the top of the `*.spec.ts` that needs them — never a separate fixture file | Rule 8, `CLAUDE.md`. See `ProductRepository.spec.ts` (`seedProduct`, `seedImage`). |
| Constraint tests | Every `CHECK` / partial unique / deferred unique gets a matching test in `apps/api/db/schema.spec.ts`, written against raw SQL | `schema.spec.ts`'s own doc comment: the ORM has no say in whether a constraint behaves as claimed; only a real insert against Postgres proves it. |
| A second rules file | **Not created.** `CLAUDE.md` is already the single source of truth for schema conventions. | A `.claude/rules/migrations.md` baseline would only diverge from it over time, and nobody would know which one is current. |

## Protocol

1. **Prereq check (hard).** `test -f docs/features/<slug>/PRD.md && test -f docs/features/<slug>/sad.md` → missing either = refuse, name which one.

2. **Read prereqs, in this order:**
   a. PRD §4 — user stories name the aggregate/entity candidates and the actors.
   b. PRD §5 — acceptance criteria give bounds: `maxLength` → `VARCHAR(N)`, an explicit
      enumerated list → `CHECK ... IN (...)`, a numeric pattern → a column precision/scale
      and a matching contract regex.
   c. sad.md §4 (Solution strategy) — storage-shape decisions are prose here, not a
      diagram stub. A sentence like "generated values live in their own table" or "no
      `deleted_at`" is a modeling decision this stage must carry through, not rediscover.
   d. sad.md §5 (Building block view) — the file list under each module tells you which
      entities are new vs. changed, and the "registration points" table (if present)
      names exactly which other files need touching (contracts, config, dependency
      cruiser).
   e. sad.md §6 (Runtime view) — walk every sequence diagram; an arrow into `pg` or a
      `Note over api, pg` that names a `table.column` is a query, and every index
      candidate must trace back to one of these. No separate `diagrams/` folder in this
      repo — the sequences live inside sad.md itself.
   f. `apps/api/db/migrations/*.ts` + `apps/api/src/modules/*/*.ts` — parse (read, don't
      connect to a live DB) what already exists, table by table.
   g. `apps/api/src/contracts/*-limits.ts`, if it exists for this feature already — reuse
      its constants instead of re-deriving bounds from prose.

3. **Decide mode per entity, not per feature.** For each entity candidate from step 2a,
   check step 2f: does a migration already create its table?
   - **Exists** → brownfield: this entity gets a delta (`ALTER`, index, or "no change —
     already covers it") in `data-model.md`, never a duplicate `CREATE TABLE`.
   - **Doesn't exist, and its delivery starts now** → greenfield: fully design it and
     write its migration in this pass.
   - **Doesn't exist, and it belongs to a later delivery** (a queue/worker/AI-call
     dependency not built yet, a "поставка 2"-style split named in sad.md §1) → design it
     completely in `data-model.md` (every column, every constraint, every index) but do
     **not** write its migration or entity class. Mark it "спроектовано, міграція —
     `<stage/поставка>`" in the Migrations table. This is the norm here, not the
     exception — see "Boundary with `feature-scaffold`" above.

4. **Aggregate roots discussion.** Ask the user (or infer from PRD + sad.md §5's file
   list): which table owns which, with `on delete cascade` marking the boundary? A child
   inside an aggregate (like `product_images` inside `products`) does not get its own
   repository or service — see rule 9, `CLAUDE.md` (a module stays flat under ~10 files).
   A row reachable only through a join (like a suggestion through its run) should not
   duplicate the parent id as a shortcut column unless a named query needs it enough to
   justify a second place the same fact can go stale.

5. **PK.** `uuid primary key default uuidv7()` for every new table, no exception to
   confirm — this is uncontested in the applied schema. Only raise it with the user if
   the PRD demands a natural key (a slug, an external id) instead.

6. **Columns, types, constraints.** For each entity:
   - `varchar(N)` for bounded strings, `N` from the matching `-limits.ts` constant or from
     PRD §5's `maxLength`.
   - `text` only for long descriptions or URLs.
   - `jsonb` only for a payload whose shape is polymorphic on another column — justify it
     in one line in `data-model.md` (see the Defaults table).
   - A closed set of values → `varchar` + named `CHECK ... IN (...)`, backed by a `const
     ... as const` union in the matching contract file, not a lookup table (see Defaults).
   - `timestamptz not null default now()` for `created_at`; add `updated_at` only when the
     entity is genuinely edited as a whole; otherwise name the specific moment
     (`started_at`, `resolved_at`, …).
   - `<!-- TBD -->` where honestly undecided — never guess to fill a cell.

7. **No relation decorators.** Every foreign key is a plain `uuid` column on the entity
   class (`@Column({ name: 'product_id', type: 'uuid' })`), never `@ManyToOne`/
   `@OneToMany`. The repository fetches the children with a second query and assembles
   them in code — this is what keeps `LIMIT`/pagination meaning aggregate roots instead of
   joined rows.

8. **Indexes — one per named query, and "no index" is a valid answer.** For every
   `table.column` a sad.md §6 sequence actually reads or writes, ask whether a sequential
   scan is already fine at this scale (50-100 rows/month per table, for most feature
   tables). `products` itself has zero secondary indexes on purpose — catalogue filters go
   through `ilike '%…%'`, which no B-tree serves anyway. Reach for an index when the query
   is a true point lookup (an idempotency key, a poll by id) or when the FK column is a
   join target with unbounded row growth over time (`product_id` on a child table). Every
   remaining candidate needs "Query it serves" filled in the Indexes table — no entry
   without one.

9. **Write `docs/features/<slug>/data-model.md`** from `./templates/data-model.md`:
   - Mermaid ER diagram — hand-composed, one clean block, not auto-laid-out.
   - `## Aggregate roots` — who owns what, and why the boundary sits there.
   - One `###` per entity: columns table, "Access patterns" (including deliberate
     no-index calls), named constraints.
   - `## Indexes` — the summary table.
   - `## Migrations` — what this pass changes, and for anything deferred, which stage/
     поставка creates it (step 3).
   - `## Test fixtures` — which `*.spec.ts` file(s) hold the seed helpers; note explicitly
     when a feature adds none (e.g., bootstrap/lookup data already exists).
   - `## Open items` — every `<!-- TBD -->`, one row each.

10. **Write the migration(s) that step 3 put in scope.** For each:
    - Generate the file with `docker compose run --rm api npm run db:migrate:new --
      <kebab-name>` — never hand-name the timestamp or the class.
    - Fill `up()` with `queryRunner.query(...)` calls: `create table`, named `CHECK`
      constraints inline, indexes as separate statements each with a one-line comment
      explaining the invariant it protects (mirror the tone of
      `1787756956906-create-products-tables.ts` — a doc comment on the class explaining
      the non-obvious choices, inline comments on anything that isn't self-evident SQL).
    - Fill `down()` as the exact reverse: `drop table if exists` in dependency order.
    - New table → also write its entity class (`PascalCase.ts`, one file, in the owning
      module's flat folder) with an explicit `type` on every `@Column` (this repo's
      `verbatimModuleSyntax` erases inferred types from decorator metadata) — unless the
      entity is deferred per step 3, in which case skip the class entirely.
    - New entity class → add it to the `ENTITIES` regex in
      `apps/api/.dependency-cruiser.cjs`. This list is intentionally named, not a glob —
      adding a class here is the explicit decision that lets `typeorm`/`pg` appear in that
      file. Flag it in the report; don't silently skip it.
    - New bounded string / enum / numeric pattern → add or extend the matching
      `apps/api/src/contracts/<feature>-limits.ts` (no dependencies in that file — see
      `CLAUDE.md` "Контракти: схеми окремо, константи окремо").

11. **Seeds**, only the buckets that actually apply here:
    - **Bootstrap** (an admin, a first row a fresh environment needs) — mirror
      `1787738400000-create-first-user.ts`: read the value from `process.env` /
      `src/config.ts`, never hardcode it, `on conflict do nothing`.
    - **Lookup data** — prefer *not* creating this table at all (see Defaults); only fall
      back to a real seeded table when the values are genuinely admin-managed data.
    - **Test fixtures** — see step 9's Defaults row: local `seedX()` functions in the spec
      that needs them.
    - **PII guard (hard rule):** never write a real-looking email/name/phone into a
      migration or a fixture. `admin@example.test`, `user-<uuid>@example.test`,
      `"Test User"` / a Ukrainian placeholder in the same non-real style.

12. **Constraint tests.** For every `CHECK`, partial unique, or deferred unique this pass
    adds, write a matching case in `apps/api/db/schema.spec.ts` — raw SQL insert that must
    reject or must succeed, in the style already there (`insertProduct`/`insertImage`
    helpers, `assert.rejects(..., /constraint_name/)`). This is the project's actual
    self-check for schema-level invariants; the ORM has no opinion on any of it.

13. **Drift check (always runs; `--drift-only` short-circuits to just this).** Entity
    classes here **are** the domain model (no separate Go/TS-struct layer to diff
    against) — so drift means: does each entity's `@Column` set match the columns the
    migrations actually created for that table? For each existing entity, compare against
    the `create table` / `alter table` statements in its migrations. Report mismatches as
    `field-without-column`, `column-without-field`, `type-mismatch`,
    `nullability-mismatch`, each with the entity file and the migration file it
    disagrees with. Propose the fix migration inline in the report — this project's scale
    doesn't warrant a separate `_drift/` staging folder; one clearly-labeled proposal is
    enough for a human to review before running it.

14. **Self-check before writing anything is final:**
    - Naming: every new table/column is `plural snake_case` / `snake_case`.
    - Every migration's `down()` fully reverses its `up()` — read them side by side.
    - Every `references other_table(id)` has a matching `create index` on that column, in
      the same migration.
    - No `@OneToMany`/`@ManyToOne` on any new entity class.
    - No new lookup table for a value set that a `const ... as const` union could hold
      instead — unless justified in `data-model.md`.
    - `apps/api/.dependency-cruiser.cjs` `ENTITIES` updated for every new entity class.
    - `docker compose run --rm --no-deps api npm run typecheck && npm run lint && npm run
      deps:check`, then `docker compose run --rm api npm run test` (this is the one
      command that needs Postgres — it builds and migrates the throwaway `_test`
      database itself).
    - `docker compose run --rm api npm run db:migrate` then `npm run db:migrate:revert`
      round-trips clean on a real database.

    Any failure → fix or surface to the user. No silent commit.

15. **Generate the report.** `docs/features/<slug>/_audit/data-model-<date>.md`:
    - **One-line result** — did this pass change the schema at all, or only design it?
    - **Generated / changed files** — every `.md`, `.ts` migration, entity class, contract
      constant this pass touched.
    - **Decisions made this pass** — anything not visible from the schema alone (a column
      doing double duty, why a fact isn't duplicated across two tables, etc.) — this is
      the section a future reader actually needs; don't let it collapse to a file list.
    - **Registration checklist** — dependency-cruiser `ENTITIES`, any `-limits.ts` touched,
      whether `db:migrate:new` was used for every new file (never hand-typed).
    - **Drift findings** — from step 13, with proposed fixes if any.
    - **Deferred entities** — from step 3's third branch, with the stage/поставка that
      owns their migration.
    - **TBDs** — every `<!-- TBD -->`, `file:line`.
    - **Next stage** — API contracts (whatever this repo's stage-10 skill is called).

16. **Propose commit.** `08+09: data-model + migrations for <slug>` (Conventional
    Commits prefix per `CLAUDE.md` would be `feat(<module>): ...` if the change lands
    inside an existing module's migration set — use judgment on which convention the
    actual diff calls for) + name the next owner/stage.

## Questions for discussion

- Aggregate roots — what owns what, and does every child really have no life without its
  parent (i.e., does `on delete cascade` actually hold)?
- Which entities are in scope for *this* delivery vs. deferred (step 3) — this changes
  whether a migration gets written today at all.
- Any closed value list the user actually wants as a real table (admin-editable data)
  instead of a code constant?
- Any `updated_at` the user wants on a new table despite it being event-shaped — say so
  explicitly; the skill defaults to precise moment-columns instead.
- Any index the user wants "just in case" with no query behind it — name the query or
  drop it.
- For a rename/drop that does touch live data — does the user want the 3-phase dance, or
  is a maintenance-window single migration acceptable at this scale?

## Definition of Done

- `data-model.md` exists: ER, aggregate roots, every entity (including deferred ones),
  every index with a named query or an explicit "no index, sequential scan is fine".
- Every in-scope schema change (step 3) has exactly one migration file under
  `apps/api/db/migrations/`, generated via `db:migrate:new`.
- Every new entity class is registered in `apps/api/.dependency-cruiser.cjs` `ENTITIES`.
- Every new `CHECK`/partial-unique/deferred-unique has a matching test in
  `db/schema.spec.ts`.
- `typecheck`, `lint`, `deps:check`, `test`, and an up→revert round-trip all pass.
- Audit report written under `_audit/`.
- Drift report (if drift found) with fix proposals inline.

## Anti-patterns

- **A relation decorator on a new entity.** `@OneToMany`/`@ManyToOne` breaks pagination
  semantics the moment a `LIMIT` is involved — always a plain FK column + a repository
  join.
- **A lookup table for a value set the code already closes.** If nothing but the app ever
  inserts a row into it, it's a union type with a `CHECK`, not a table.
- **`updated_at` on every table by reflex.** Name the moment, or omit it.
- **An index with no named query behind it.** Every index costs writes; "might need it
  later" isn't a query.
- **`TEXT` for everything.** Bounded strings get `varchar(N)` from the matching
  `-limits.ts` constant.
- **Triggers or stored procedures.** `CHECK` is fine for a bound on one row's own value;
  behavior stays in the app.
- **Hand-typing a migration filename or class name.** Always `db:migrate:new`.
- **A new entity class not added to `.dependency-cruiser.cjs`'s `ENTITIES`.** `deps:check`
  won't catch this by itself if the file otherwise looks like a normal module file — it's
  a manual step this skill must not forget.
- **A separate migration-fixture file.** Fixtures live as local functions in the spec that
  needs them (rule 8, `CLAUDE.md`).
- **Writing a migration for an entity deferred to a later delivery.** Design it fully;
  leave the DDL for when that slice is actually built (see "Migration write policy" /
  step 3's third branch).
- **A second rules file under `.claude/rules/`.** `CLAUDE.md` is already canonical;
  document any deviation in the audit report's table instead of a competing file.
- **Real-looking PII in a seed or a fixture.** `example.test` only.
