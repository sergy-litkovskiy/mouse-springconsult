# /release-notes — notes для наявного релізу

Правила тексту — **лише** в `.github/prompts/release-notes.md`: прочитай його першим і не
додавай своїх.

## 1. Реліз

Версія — з аргументу, інакше перша `## [X.Y.Z]` у `CHANGELOG.md` на `origin/main`.

```bash
git fetch origin --tags
gh api repos/{owner}/{repo}/releases \
  --jq '.[] | select(.tag_name == "vX.Y.Z") | {id, name, draft, author: .author.login, updated_at}'
```

Список, а не `gh release view vX.Y.Z`: на одному тезі буває кілька релізів — чернетка
бота і реліз, створений людиною поруч замість публікації чернетки, — а `view` і `edit`
за тегом мовчки беруть опублікований.

- Жодного → **стоп**: реліз створює `release.yml` після мерджу Release-PR; якщо тег є, а
  чернетки немає — перезапусти в Actions останній прогін `Release`.
- Більше одного → **стоп**: покажи їх таблицею і спитай, який правити і чи прибрати зайвий.
- Рівно один → запам'ятай його `id` і `updated_at`; далі працюєш лише з ним.

## 2. Текст

Візьми тіло секції `## [X.Y.Z]` з `CHANGELOG.md` і напиши notes за правилами промпту.

Тіло релізу збери так само, як `release.yml`:

```markdown
<notes>

## Зміни

<секція CHANGELOG без заголовка версії>

**Повний diff:** https://github.com/<owner>/<repo>/compare/vPREV...vX.Y.Z
```

Рядок diff — лише коли є попередня версія в `CHANGELOG.md`.

## 3. Запис

Покажи тіло в чаті, назви реліз, який правиш (`id`, назва, чернетка чи опублікований), і
**зупинись**. Після явного «так» спершу повтори список з кроку 1: поки людина читала, вона
могла опублікувати, перейменувати чи створити реліз. Змінився набір релізів на тезі або
`updated_at` обраного → **стоп**, покажи, що змінилось, і спитай знову.

Лише тоді — запис за `id`, не за тегом:

```bash
gh api -X PATCH repos/{owner}/{repo}/releases/<id> -F body=@<файл у scratchpad>
```

Змінюється лише текст: опублікований реліз лишається опублікованим, чернетка —
чернеткою. Публікує людина.
