# Skill: feature-api-forge

Генератор API-контракту для mouse-springconsult: **OpenAPI 3.1** для синхронних HTTP-ендпоінтів
+ `events.md` для асинхронних подій (pg-boss). Контракт **ніколи не пишеться руками з чистого
аркуша** — це детермінований проєкт вхідних артефактів (`data-model.md`, sequence-діаграми з
`sad.md` §6, PRD §4, а коли модуль частково реалізований — уже написані zod-контракти в
`apps/api/src/contracts/`) у схему OpenAPI 3.1. Пише
`docs/features/<slug>/contracts/openapi.yaml` + `docs/features/<slug>/contracts/api-sync-report.md`.

Це локальний **стейдж 05** цього проєкту (SDLC-нумерація тут своя — дивись комбіновані коміти
`01:`…`05:` в історії; курсовий скіл називає той самий крок стейджем 10, номер значення не
має, порядок після SAD + data-model — має). Контракт фіксується до того, як за нього
береться фронт: `apps/web` бере типи з `@contracts/*`, а не з `openapi.yaml` — цей документ
для людини, іншого консюмера й дрейф-чеку, не рантайм-джерело типів (див. «Codegen» нижче).

## Чому цей скіл існує окремо від `plugin:api-forge`

Курсовий `api-forge` кодує узгоджений мінімум з публічних гайдлайнів (Microsoft/Google/
Zalando) — правильний дефолт для проєкту з нуля, без власної історії. mouse-springconsult
таку історію вже має: перший реальний прогін (`product-creation-flow`, коміт `05`) виявив
сім розбіжностей між дефолтом скіла й тим, що вже живе в коді
(`docs/features/product-creation-flow/contracts/api-sync-report.md`, розділ «Розбіжності зі
скіл-дефолтами»). Цей скіл більше не називає їх розбіжностями — вони тут дефолт, бо
[дефолти SDLC-скілів поступаються CLAUDE.md](/Users/serhii/.claude/projects/-Users-serhii-projects-mouse-springconsult/memory/sdlc-skill-defaults-yield-to-claude-md.md).
Розбіжність варта таблиці лише тоді, коли контракт відхиляється **від дефолтів нижче**, не
від курсового скіла.

корисним (наприклад, «endpoint-level sequences в sad.md §6 не знайдено → гілки помилок
виведені лише з acceptance criteria PRD, можливо пропущено 403 not-owned»).

## Сценарії A vs B

### Сценарій A — data-model.md існує (типовий для цього репо)

Контракт **виводиться** з моделі. Кожне поле має `origin` у типізованій сутності.
Обмеження (`maxLength`, `pattern`, `enum`) трасуються до DDL (`varchar(N)`, `CHECK`,
`NUMERIC(p,s)`). Коди помилок виводяться з обмежень (`UNIQUE` → `<entity>_already_exists`
або конкретніший код на розсуд домену — дивись «Неймспейс кодів помилок» нижче).
`unresolved_origins` **порожній** — окрім полів, які сам `data-model.md` називає
нерозв'язаними в `## Open items` (це не хиба скіла, а чесна передача невизначеності
джерела; продукт-creation-flow має такий прецедент — форма `FieldSuggestion.value` для
`price`).

Дрейф-чек (крок 17) звіряє модель і контракт поле в поле. Розходження в сценарії A — сигнал
людині, яке з двох джерел правильне.

### Сценарій B — data-model.md відсутній (fallback)

Контракт **виводиться** з PRD §4 acceptance criteria + sequence-діаграм + неймспейсингу
sad.md §6. Типи менш точні (`string` без `maxLength`, без enum-патернів). Коди помилок
виводяться з `alt`-блоків sequence, не з обмежень моделі.

`unresolved_origins` перелічує кожне поле, чиє походження — «виведено з PRD/sequence,
потребує підтвердження, коли з'явиться data-model.md». Це **не помилка** — це **декларована
неповнота**, видима команді.

### Reconcile (`--reconcile`)

Коли `data-model.md` з'являється після прогону в сценарії B, перезапустити скіл з
`--reconcile`. Він:

1. Перечитує входи (тепер із data-model.md).
2. Перемикає сценарій B → A.
3. Уточнює типи: `string` отримує `maxLength` там, де є DDL.
4. Підвищує `low`-впевненість origin до `high`.
5. Спорожнює `unresolved_origins` (крім того, що сам data-model.md лишає в Open items).
6. Виявляє поле, яке **мало** виведений з PRD origin, але **тепер розходиться** з
   моделлю — це справжній дрейф, не застаріла неповнота.

`--update` (без зміни сценарію) перечитує всі входи й регенерує YAML на місці, зберігаючи
`info.version`; корисно, коли sad.md чи data-model.md змінились, але жоден з них не з'явився
чи не зник.

## Дефолти mouse-springconsult

На відміну від курсового скіла, це не «узгоджений мінімум з публічних гайдлайнів», а
конвенції, вже підписані кодом і `CLAUDE.md` цього репо. Коли контракт відхиляється від
таблиці нижче — саме це йде в `api-sync-report.md` як розбіжність, з поясненням чому.

| Тема | Дефолт mouse-springconsult | Джерело / чому |
|---|---|---|
| Версія OpenAPI | `3.1.0` | JSON Schema 2020-12, `nullable` через `type: [string, null]` — так само, як у наявному `openapi.yaml`. |
| Форма помилки | `{error: {code, message, details?}}` — **обгорнуто** в `error`, не пласко | Форма `apps/api/src/contracts/error.contract.ts` і фактичного error-handler'а в `api.ts`. Контракт узгоджується з кодом, не навпаки. |
| Неймспейс кодів помилок | Пласкі snake_case, **без** префікса модуля крапкою (`gallery_full`, `image_not_found`, `invalid_credentials`) | Так виглядають усі коди в `apps/api/src/contracts/error-codes.ts` (auth) і в наявному `openapi.yaml` (products) — дотована крапка (`<module>.<error_name>`) не має жодного прецеденту в коді. Модуль-джерело коду виявляється з ендпоінту й HTTP-статусу, не з префіксу рядка. |
| Пагінація списків | **Offset** (`page`/`pageSize` у запиті, `{items, total, page, pageSize}` у відповіді) | Так реалізовано в `productListQuerySchema` + `ProductController.list`; 50–100 товарів/міс й один-два адміни не мають конкурентного запису, заради якого курсорна стабільність сторінок щось вирішує. Якщо колись зʼявиться список із високим темпом вставок під час читання — тоді курсор, і саме тоді, а не про запас. |
| Авторизація | `apiKey`/`cookie`, ім'я `mouse_session` (значення бере `config.session.cookieName`, не хардкодиться в шаблоні) | JWT (HS256, `jose`) у HttpOnly-cookie — [ADR 0002](../../../docs/adr/0002-auth-jwt-and-typeorm.md), `apps/api/src/modules/auth/CLAUDE.md`: «Ні `Authorization: Bearer`, ні localStorage — SPA і API на одному домені». Ролей немає: перевірка — активна сесія (`sessionGuard`), не scope/permission. |
| Версіювання URL | **Без сегмента версії**: `/api/<resource>`, не `/api/v1/<resource>` | `infra/caddy/Caddyfile` (`handle_path /api/*`) знімає префікс, Fastify реєструє голі шляхи. Один внутрішній адмін-клієнт, зовнішніх консюмерів немає — вводити версію нема для кого. Зʼявиться другий консюмер — тоді й розмова про версіювання, не раніше. |
| Регістр полів на дроті | camelCase (не snake_case із Zalando) | Так повертає вже реалізований `productSchema` (`titleProm`, `publishedOlx`). БД — snake_case, TS/JSON — camelCase; це саме розмежування, яке CLAUDE.md називає для шару БД, і воно не поширюється на дріт. |
| Гроші | `type: string`, `pattern: '^\d{1,10}(\.\d{1,2})?$'`, ніякого `type: number` | CLAUDE.md «Гроші»: `decimal(12,2)` у БД доходить до браузера без жодного перетворення. Патерн — той самий, що `productConstraints.pricePattern`. |
| Час | `type: string, format: date-time` (ISO 8601, UTC) | CLAUDE.md «Час»: `timestamptz` у БД, форматування — на клієнті; контракт не вгадує часовий пояс. |
| Генерація ID | `uuid` без `format` окрім `format: uuid`; генерується **в БД** (`default uuidv7()`), не в застосунку | Так уже в міграціях (`create-products-tables`): час-упорядкований UUID v7 за замовчуванням колонки. Курсовий дефолт «v7 у застосунку, щоб клієнт передбачив id до запиту» тут не застосовний — жоден ендпоінт цього репо не потребує id до INSERT. |
| Ідемпотентність мутацій, що можуть повторюватись | Ключ обчислює **сервер** з бізнес-полів запиту (наприклад, `(productId, scope, вхідна версія)`), зберігає як `UNIQUE`-колонку в таблиці запуску — **не** заголовок `Idempotency-Key` від клієнта | Прецедент — `product_preparation_runs.idempotency_key UNIQUE`; повторний виклик з тим самим входом повертає наявний запуск (`200`), новий запуск — `201`. Заголовок від клієнта підходить для ендпоінтів без природного дублікатора; коли є — сервер сам знає, що є повтором. |
| Валідація в специфікації | `pattern`/`enum`/`maxLength` обов'язкові для обмежених полів | Подвійна безпека: контролер валідує ще раз zod-схемою, але контракт і аудит тримають узгодженість з БД. |
| Повторне використання схем | `$ref` обов'язковий; inline-схеми — **заборонені** | Один запис форми на тип — менше дрейфу між ендпоінтами. Дивись Ban-list нижче. |
| Заборонено | `nullable: true` (стиль 3.0), реальні PII в `example`, `additionalProperties: true` на response-схемах, inline-схеми поза `components/schemas` | Стильовий leak зі старої версії; PII в Swagger UI; витік внутрішнього поля; дрейф без єдиного джерела форми. |

Коли ADR перекриває дефолт (наприклад, майбутній ADR приписує інший механізм сесії для
нового зовнішнього консюмера) — звіт фіксує «перекрито ADR-NNNN», щоб перекриття було
задокументоване, а не тихе.

## Ban-list (жорсткі перевірки перед комітом)

Скіл відмовляється комітити контракт, що порушує це, і замість цього називає порушення
людині:

1. **Inline-схема замість `$ref`.** Будь-який `schema:` під `requestBody`/`responses`, що
   не є або примітивом (`{type: string}` для одного query-параметра), або `$ref` на
   `components/schemas/<Name>` — заборонено. Виняток — `PreparationRunCreateRequest`-подібні
   одноразові request-схеми з одним-двома полями без повторного використання: їх можна
   тримати inline, **якщо** вони ніколи не зʼявляються в іншому `requestBody`/`response`; щойно
   зʼявляються вдруге — виносити в `components/schemas`.
2. **Реальні PII в `example`.** Приклад — вигаданий товар/юзер, а не реальний з R2/БД.
   Домен цього репо — комісійні товари, тож приклад типу «Кавомашина DeLonghi ECAM, б/у» —
   ОК (вигаданий товарний опис, не персональні дані), а реальний email, телефон, ПІБ
   реального продавця чи адміна — ні. Плейсхолдер-формат: `<...>@example.test`,
   `+380 00 000 00 00`, «Тестовий Юзер» — так само, як курсовий дефолт.
3. **`nullable: true`.** Тільки `type: [string, null]` (OpenAPI 3.1 / JSON Schema
   2020-12).
4. **Response-схема без `required` на нетривіальному об'єкті.** Кожен `type: object` у
   `components/schemas` перелічує `required`, якщо хоч одне поле дійсно завжди присутнє —
   інакше клієнтський код повний `?.` там, де контракт міг це виключити.

Якщо ban-list ловить ≥1 порушення — скіл зупиняється, показує список, і генерує решту
контракту без порушеного місця, а не мовчки виправляє на власний розсуд (виправлення форми
запиту — рішення людини, не скіла).

## Codegen

Цей репо **не** генерує TypeScript-типи з `openapi.yaml` для рантайму: фронт бере типи з
`@contracts/*` (`apps/api/src/contracts/*.contract.ts`) напряму — CLAUDE.md «Контракти:
схеми окремо, константи окремо». `openapi.yaml` тут — контракт-документ для людини й
дрейф-чек, не джерело codegen для FE. Тому конкретна команда генерації існує тільки як
**інструмент верифікації**, не як крок збірки:

```bash
# Згенерувати .d.ts із контракту і звірити його вручну/по фікстурі проти
# ручного zod-типу — так само, як зроблено в rehearsal-прогоні
# product-creation-flow (api-sync-report.md, розділ «Прогін --update»).
npx --yes openapi-typescript@7 \
  docs/features/<slug>/contracts/openapi.yaml \
  -o /tmp/openapi-types.d.ts
```

Якщо колись зʼявиться зовнішній консюмер поза `apps/web` (інтеграція з Prom/OLX API, скажімо)
— тоді codegen у білд-пайплайн, і ця секція переписується разом з ADR на цю тему. Поки що
немає для кого.

## Протокол

1. **Перевірка передумов (жорстка).** `test -f docs/features/<slug>/PRD.md` → exit ≠ 0 =
   відмова з посиланням на `feature-write-prd`. Відсутність data-model.md — **не** відмова,
   а перемикач на сценарій B.
2. **Визначити сценарій.** A, якщо `docs/features/<slug>/data-model.md` існує, B — інакше.
   Назвати користувачу, який сценарій визначено і які входи знайдено/пропущено.
3. **Прочитати обов'язкові входи.** PRD (AC → ендпоінти + правила валідації), data-model,
   якщо A (форми сутностей, типи, обмеження).
4. **Прочитати опційні входи (авто-детект).** Для кожного з `sad.md`, `idea-brief.md`,
   `adr/*.md`, наявного `apps/api/src/contracts/<feature>.contract.ts` +
   `<feature>-limits.ts`: якщо присутній — розпарсити й показати рядок «знайдено», якщо
   відсутній — «пропущено» з наслідком. Ніколи не відмовляти через відсутність — це
   збагачення, не передумова.
5. **Обрати стиль.** HTTP REST (OpenAPI 3.1) — дефолт для ресурсної адмінки. GraphQL /
   AsyncAPI — тільки якщо явно попросили; для цього репо (одна адмінка, черга в Postgres,
   без окремих consumer-сервісів) REST + events.md для pg-boss задач покриває все.
6. **Скопіювати шаблони.** З `./templates/`:
   - `openapi.yaml` → `docs/features/<slug>/contracts/openapi.yaml` (або оновити на
     місці, якщо вже існує).
   - `events.md` → `docs/features/<slug>/contracts/events.md` (якщо є pg-boss job з
     власною подією, вартою документування окремо від коду черги).
7. **Версіювання.** Без сегмента версії (`/api/<resource>`) — дефолт. Інакше — тільки якщо
   ADR явно приписує інше.
8. **Ендпоінти на кожен AC.** Метод + шлях + request-схема + response-схема + помилки. У
   сценарії A поля трасуються до колонок сутності data-model.md; у сценарії B — виводяться з
   назв полів PRD + повідомлень sequence.
9. **Гілки помилок з `alt`-блоків (коли є sequence).** Для кожного ендпоінту, покритого
   Mermaid `sequenceDiagram` у sad.md §6: розпарсити `alt … else … end` і додати запис
   `responses` на гілку (`alt not found` → `404 <entity>_not_found`, `alt not owner` →
   `403 <entity>_not_owned`, `alt invalid state` → `409 <entity>_invalid_state`). Це
   закриває типову сліпу зону PRD — там happy path + 2-3 помилки, sequence вичерпно
   перелічує гілки, включно з 403 not-owned, який PRD часто не називає.
10. **Модель помилки.** Уніфіковано `{error: {code, message, details?}}`. `code` — плаский
    snake_case без крапки-неймспейсу (дефолти вище). HTTP-статус: 4xx клієнт, 5xx сервер. Не
    `{"error": "щось пішло не так"}` без коду.
11. **Ідемпотентність.** Мутуючі + повторювані ендпоінти (POST зі стороннім ефектом, який
    коштує грошей чи ставить чергову задачу) — ключ обчислює сервер із бізнес-полів запиту,
    не заголовок клієнта (дефолти вище). Якщо sequence показує `Note over API, Worker: retry`
    для ендпоінту — позначити ключ обов'язковим.
12. **Пагінація.** Offset (`?page=&pageSize=`) для списків, відповідь
    `{items, total, page, pageSize}` — дефолт цього репо. Курсор — тільки якщо явно
    обґрунтовано (висока конкурентність запису на цей саме список).
13. **Асинхронні задачі (pg-boss).** Для кожної задачі, поставленої в чергу з ендпоінту: назва
    (`<feature>.<action>`), схема payload (JSON Schema), producer, consumer (`worker.ts`),
    поведінка retry (pg-boss `retryLimit`/`retryDelay`, не окремий DLQ-топік — DLQ немає, є
    `retryLimit` вичерпано → рядок лишається у `failed`-стані в тій самій таблиці pg-boss).
    Якщо sequence має `API->>Worker: enqueue` — вивести перелік задач з цих повідомлень і
    попередньо заповнити `events.md`.
14. **Приклади.** Кожна операція — request-приклад + 200/201-приклад + приклад помилки.
    Плейсхолдер-дані домену (вигаданий товар), ніколи реальні PII (Ban-list, п.2).
15. **Lint.** Запропонувати `npx --yes @stoplight/spectral-cli lint
    docs/features/<slug>/contracts/openapi.yaml`. Не вписано в `package.json` жодного з
    `apps/api`/`apps/web` — якщо це стає рутиною, додати в `make sdlc-check` окремою задачею,
    не цим прогоном.
16. **Mock-сервер.** Запропонувати `npx --yes @stoplight/prism-cli mock
    docs/features/<slug>/contracts/openapi.yaml`. Єдиний консюмер (`apps/web`) має до нього
    доступ локально.
17. **Inline дрейф-чек (5 пунктів) + `api-sync-report.md`.** Звірити згенерований
    `openapi.yaml` з усіма прочитаними артефактами. Звіт має три секції:

    **Секція A — таблиця походження полів.** Один рядок на пару `(operation, поле схеми)`:
    `шлях_схеми | origin | confidence`. `high` — сценарій A з відповідним типом DDL; `medium`
    — виведено з PRD або з бізнес-правила без прямої колонки (наприклад,
    `discardedKeywordsCount` — рахує сервіс, не колонка); `low` — виведено лише з назви
    повідомлення sequence, форма не підтверджена жодним іншим джерелом.

    **Секція B — знахідки дрейфу.** Той самий 5-пунктовий чеклист (✓/✗ з однорядковим
    діагнозом на ✗):

    1. **Ендпоінт ↔ data-model** — кожен ендпоінт мапиться на ≥1 запит/мутацію проти
       сутності в `data-model.md`. У сценарії B — кожен ендпоінт мапиться на sequence
       (моделі немає).
    2. **Коди помилок ↔ доменні сентінели** — кожен `code` в `ErrorResponse` має константу
       в `<Feature>Errors.ts` (взірець — `AuthErrors.ts`). Якщо файл ще не існує (модуль на
       ранній стадії) — **waived, не ✗**, з приміткою «специфікація для стейджу
       break-tasks», а не мовчазний пропуск.
    3. **Валідація ↔ обмеження БД** — `maxLength`/`pattern`/`enum` в OpenAPI збігаються з
       `VARCHAR(N)`/DB `CHECK`/код-обмеженнями з `<feature>-limits.ts` (сценарій A; сценарій
       B — «відкладено до reconcile»).
    4. **Сутність ↔ ендпоінт** — кожна сутність з `data-model.md` обслужена ≥1 ендпоінтом,
       або явно позначена «навмисно внутрішня» (сценарій A).
    5. **OpenAPI ↔ sequence** — endpoint-level sequence в sad.md §6 узгоджені з HTTP-
       методами/шляхами/кодами `openapi.yaml`. Якщо sad.md навмисно не називає методи/шляхи
       (делегує це стейджу api-forge — типово для цього репо), звірка йде по репліках
       («ставить задачу з ключем ідемпотентності», «перевіряє ліміт частоти»), а не по рядках.

    **Core checks** (1, 2, 3), що впали — блокер користувачу. **Supporting checks** (4, 5) —
    follow-up у звіті, не блокер.

    **Секція C — unresolved_origins.** Порожня в сценарії A, окрім того, що сам
    `data-model.md` називає в `## Open items`. У сценарії B — перелік полів з поточним
    origin і тим, що уточнить reconcile.

18. **Самоперевірка проти DoD.** Lint запропоновано (не обов'язково пройдено — інструмент
    не вписаний у CI), приклади на всіх операціях, модель помилки з кодами, mock-сервер
    запропоновано, `api-sync-report.md` core checks (1–3) усі ✓ або явно waived зі
    обґрунтуванням, сценарій явно зафіксовано.
19. **Запропонувати коміт.** Формат — той самий, що вже в історії проєкту:
    `<NN>: API contract for <slug> via feature-api-forge`, де `<NN>` — наступний номер
    після останнього SDLC-стейджу, закомiченого для цього slug (перевірити `git log
    --oneline | grep <slug>` чи еквівалент, а не хардкодити число). Наступний власник —
    Backend Lead → стейдж break-tasks (реалізувати доменні помилки за переліком з Section B
    п.2).

## Інваріанти

- **Ніколи не вигадувати поля.** Якщо в жодному вхідному артефакті немає origin для поля —
  скіл відмовляється його додавати й питає людину, звідки воно має взятись.
- **Ніколи не приховувати поле мовчки.** Якщо поле зникло з `data-model.md`, воно лишається
  в YAML з коментарем `# stale` і потрапляє в звіт — людина вирішує, прибрати з контракту чи
  повернути в модель.
- **Ніколи не редагувати джерела.** Тільки читання. Правка `data-model.md`/`PRD.md`/sequence
  — робота людини.
- **Іменування схем — доменною мовою `data-model.md`**, не Go/TS-ідіомами (тип TypeScript,
  який згенерує `openapi-typescript` для дрейф-чеку, — похідне, не першоджерело).
- **Ніколи не піднімати `info.version` мовчки.** Семвер підвищує людина явно, з
  CHANGELOG-записом (якщо CHANGELOG заведено для фічі) чи описом у PR.

## Конфлікти — людина вирішує

| Конфлікт | Дія скіла |
|---|---|
| Поле в `data-model.md` без жодної історії в PRD | Додати поле в схему з приміткою `# unused-in-prd` в `api-sync-report.md`; спитати людину. |
| Sequence посилається на операцію, яка не мапиться на жоден ендпоінт результату | Позначка `# orphan-sequence` у звіті; спитати людину (забутий ендпоінт? внутрішня джоба?). |
| Правило валідації PRD суперечить обмеженню DDL (`maxLength 300` в PRD проти `varchar(200)` в DDL) | Взяти суворіше значення; позначити обидва в звіті. Людина вирішує, яке джерело неправильне. |
| Наявний `openapi.yaml` має поля, яких немає в жодному джерелі | Лишити з коментарем `# manual-addition`; позначити в звіті. |

Якщо в одному прогоні зʼявляється ≥3 позначки — зупинитись, показати перелік користувачу,
спитати продовжувати чи спершу виправити джерела.

## Анти-патерни

- «Контракт після коду» — фронт інтегрується проти змін, що ламають. Contract-first.
- Помилка вільним текстом: `{"error": "щось пішло не так"}`. Тільки
  `{error: {code, message, details?}}`.
- Версіювання через `?v=2` query-параметр — нестандартно, ламає кеш; і взагалі не потрібно
  цьому проєкту (дефолти вище).
- Ідемпотентність «якщо не лінь» для мутуючих + повторюваних. Обов'язковий ключ, який рахує
  сервер, з описаною поведінкою на повтор.
- Асинхронна задача без схеми payload — pg-boss consumer падає на першій зміні, що ламає.
- Операції без прикладів. Lint проходить, але той, хто реалізує, не розуміє, що саме такий
  запит означає.
- Назви методів у sequence-діаграмах і в API різні. Інженер, що заходить у код вперше,
  потрапляє в пастку.
- **Пропустити дрейф-чек, бо «специфікацію щойно згенеровано, звісно вона збігається»**.
  5-пунктова перевірка існує саме тому, що генерація може збігтись із PRD-як-прочитаним, і
  розійтись із data-model чи sequence (різні файли, різні моменти написання). Чисті 5/5 ✓
  дешево показати; мовчазний ✗ у проді — ні.
- **Гілки помилок лише з PRD.** PRD типово перелічує happy path + 2-3 помилки. Sequence
  вичерпно перелічує `alt`-гілки, включно з 403 not-owned і станами конкурентної зміни.
  Пропуск sequence-збагачення лишає сліпі зони.
- **Приховати сценарій B, ніби він повний.** Сценарій B — валідний стан, не недороблений.
  `unresolved_origins` має бути видимим. Вдавати, що контракт повністю типізований, коли це
  не так, готує команду до мовчазного дрейфу, коли модель нарешті зʼявиться.
- **`nullable: true`** (стиль 3.0) в 3.1-документах. `type: [string, null]`.
- **Реальні PII в `example`-блоках.** Плейсхолдери (Ban-list, п.2).
- **Inline-схема замість `$ref`** там, де форма використовується вдруге (Ban-list, п.1).
- **Курсорна пагінація «про всяк випадок»** там, де офсет уже реалізовано і масштаб не
  вимагає іншого (Дефолти, «Пагінація»).

## Джерела дефолтів

Публічні гайдлайни, з яких курсовий скіл починав, і які ці дефолти **перекривають**, коли
розходяться з уже підписаним кодом цього репо (таблиця вище прямо називає, де саме):

- **Microsoft REST API Guidelines** — https://github.com/microsoft/api-guidelines. Форма
  помилки з машинним `code`.
- **Google AIP** — https://google.aip.dev/. Ресурсно-орієнтовані шляхи, доменний неймспейс
  кодів помилок (тут — спрощено до пласкої форми, дивись дефолти).
- **Zalando RESTful API Guidelines** — https://opensource.zalando.com/restful-api-guidelines/.
  Курсорна пагінація (тут перекрито офсетом — дефолти вище), JSON-only відповіді.
- **OpenAPI 3.1 specification** — https://spec.openapis.org/oas/v3.1.0. Повна сумісність з
  JSON Schema 2020-12 — єдиний пункт, де курсовий дефолт і дефолт цього репо збігаються
  без застережень.
- **Прецедент самого репо** — `docs/features/product-creation-flow/contracts/openapi.yaml`
  + `api-sync-report.md`. Перший реальний прогін, з якого виведено таблицю дефолтів вище;
  за розбіжністю з ним варто йти сюди раніше, ніж у публічний гайдлайн.
