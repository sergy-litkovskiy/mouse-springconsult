# Events — <feature>

Черга — pg-boss поверх PostgreSQL (CLAUDE.md: «Не додаємо Redis/RabbitMQ — черга живе в
Postgres, поки навантаження це дозволяє»). Немає окремого DLQ-топіка й окремого брокера:
вичерпаний retry лишає рядок job'и у стані `failed` в тій самій таблиці pg-boss, видимий
тим самим `SELECT`, яким адмін дивиться інші job'и.

## Job: `<feature>.<action>`

**Producer:** `<Feature>Controller` (ставить job під час обробки `<HTTP-метод> <шлях>`).
**Consumer:** `apps/api/src/worker.ts` → `modules/<feature>/index.ts` public API.
**Retry:** `retryLimit: <N>`, `retryDelay: <секунди>` (pg-boss-опції `send()`/`work()`, не
довільне число — узгодити з тим, скільки коштує повтор: AI-виклик коштує грошей і часу,
файлова операція — ні).
**Ідемпотентність:** ключ обчислює сервер із бізнес-полів запиту (не заголовок клієнта —
дефолти `feature-api-forge`), зберігається як `UNIQUE`-колонка на стороні застосунку, не
на стороні pg-boss (pg-boss сам не гарантує exactly-once за бізнес-ключем).

### Payload

```json
{
  "<feature>Id": "<uuid>",
  "<поле>": "<тип>"
}
```

**Обовʼязкові поля:** `<...>`.
**Політика зворотної сумісності:** тільки додавання нових опційних полів; видалення чи
перейменування — нова назва job'и (`<feature>.<action>.v2`), стара лишається, поки живі
задачі в черзі.

## Стан і полінг

Якщо HTTP-клієнт має дізнатись про завершення job'и (типовий кейс — фронт полить статус),
статус job'и — окрема колонка на бізнес-сутності (`status`, `error_code`), а не окремий
ендпоінт "стан pg-boss job'и за id" — id job'и pg-boss не перетинає межу API (наявний
прецедент — `product_preparation_runs.status`, не `pgBossJobId` в response-схемі).

## Спостережуваність

- Лог: pino, structured, без повних тіл payload'ів, якщо там зображення чи великий текст
  (CLAUDE.md «Логи»).
- Метрика на "скільки job'ів у `failed`" — ручний запит адміна до появи дашборда; окремого
  моніторингу для черги, поки один-два адміни, не заводимо.
