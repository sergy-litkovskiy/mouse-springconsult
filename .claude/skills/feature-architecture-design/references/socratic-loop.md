# Socratic-цикл — крок 7: секція за секцією, з ADR-gate і записом у файл

## TL;DR

Крок 7 — діалог з користувачем по кожній секції SAD:

1. Skill **показує всю секцію відразу** й нумерує рішення всередині.
2. Питає **по одному рішенню** через `AskUserQuestion`.
3. Користувач обирає одну з **чотирьох дій**: **Прийняти** / **Виправити** /
   **Винести у відкрите питання** (`Save as OQ`) / **Викинути** (`Drop`).
4. Для кожного Прийнятого рішення прогоняється **blast-radius gate**. Спрацював —
   народжується ADR у форматі MADR.
5. Skill **записує секцію та її ADR у файли** й іде далі. Назад до записаної секції не
   повертається — розходження між секціями ловить критик кроку 8.

**Коміту тут немає.** Коміт один, наприкінці кроку 8. Файли пишуться відразу, щоб Ctrl-C
коштував тільки поточну секцію.

---

## Контракт

Для кожної з §1 → §12 по черзі:

1. **7a. Показати запропоновану секцію** одним повідомленням — тіло тексту плюс нумерований
   перелік рішень усередині. Це дає користувачеві загальну картину до того, як він почне
   вирішувати поштучно: дублікати, дірки й «цю секцію взагалі не треба» видно саме тут.
2. **7b. Пройти рішення поштучно** — один `AskUserQuestion` на рішення, чотири дії.
3. **7c. Застосувати переходи** до секції в пам'яті, у міру надходження відповідей.
4. **7d. Прогнати blast-radius gate** на кожному Прийнятому рішенні (не на Edit / Drop /
   Save-as-OQ — з них ADR не народжуються). Спрацював хоч один критерій — спавн ADR
   (див. [blast-radius-heuristic.md](./blast-radius-heuristic.md)).
5. **7e. Записати секцію в `sad.md`** з усіма застосованими переходами + записати файли ADR,
   що народилися в 7d. **Без коміту.**
6. **7f. Наступна секція.** Skill **не повертається** до вже записаної. Розходження між
   секціями (§4 обіцяє одне, §6 малює інше) — робота критика кроку 8.

## Каталог типів рішень

Секція може містити суміш типів. Чотири дії однакові для всіх; різниця — у формі опцій
(див. [ask-examples.md](./ask-examples.md)).

- **Стратегічне** — §4, зрідка §7. Набір з 2-4 опцій, рекомендована перша.
  ADR-gate спрацьовує майже завжди.
- **Модульне** — §5. Межа модуля, де лежить оркестрація, що йде в `contracts/`.
  ADR-gate спрацьовує часто (зачіпає ≥2 модулі).
- **Наскрізний пакет** — §8. Дві опції: «лишити дефолти `CLAUDE.md`» / «перекрити для цієї
  фічі». ADR-gate спрацьовує рідко — це рівень конвенції.
- **Сценарій якості** — §10. Набір опцій тут зазвичай марний: числа приходять з PRD §6.
  Типове вирішення — Прийняти / Виправити спосіб перевірки / Винести у відкрите питання.
- **Рядок ризику** — §11. Складається автоматично з логу правок, PRD §8 і розходжень кроку 3.
  Користувач приймає дослівно або править серйозність, мітигацію, власника.
- **Відкрите архітектурне рішення** — окремий випадок рядка ризику, що народжується з
  будь-якого `Save as Open Question`. Skill пише рядок §11 у момент вирішення; окремого
  питання по ньому користувач не бачить — він уже погодився, обравши цю опцію.

## Чотири дії з рішенням

- **`Прийняти`** → рішення лишається дослівно. Запису в лог правок немає. Прогоняється
  blast-radius gate (7d). Далі — наступне рішення.

- **`Виправити`** → користувач одразу дає нове формулювання, іншу опцію, іншу серйозність;
  skill перегенеровує рішення з новим обмеженням і питає **ще один раз** по новій версії.
  Друга відповідь остаточна. Запис у лог з `action: "edit"`.

- **`Винести у відкрите питання`** → рішення прибирається зі своєї секції, а в таблицю §11
  дописується рядок такої форми:

  ```
  | Open architectural decision: <заголовок> | Open question | Resolve before <етап або YYYY-MM-DD>; <обґрунтування користувача дослівно> | <owner> |
  ```

  Owner і due (дата **або** тригер-етап, як «до `break-tasks`») **обидва обов'язкові** —
  skill ставить додаткове `AskUserQuestion` одразу після вибору цієї опції. Порожнє
  будь-яке з двох — вирішення **понижується до `Drop`** з видимим попередженням.

  Колонка Severity приймає літерал `Open question` замість Low/Medium/High — саме він
  відрізняє відкладене рішення від звичайного ризику (використовується критиком F3 і
  чеклистом). Запис у лог з `action: "save_as_oq"`. **ADR не народжується** — відкладення
  не є рішенням.

- **`Викинути`** → рішення прибирається з секції. Дві гілки:
  - **Рішення обов'язкове** (напр. межа модуля в §5 — вона є в кожної фічі) → skill питає
    ще раз із **переформульованим** набором опцій. Тільки один повтор; викинув удруге —
    ескалація в `Save as Open Question` з owner = Serhii, due = «до наступного проходу»,
    і попередженням.
  - **Рішення необов'язкове** (напр. ще один сценарій відмови в §6 понад happy path) →
    просто лишається поза документом.
  - Запис у лог з `action: "drop"`.

`Cancel` і `Reject` — синоніми `Drop`: той самий перехід, той самий запис у лог.

Кожна опція має `description`, який називає наступний механічний крок skill-а — див.
[ask-examples.md](./ask-examples.md).

Переходи застосовуються до секції **в пам'яті** після кожної відповіді. Файл пишеться
один раз, у 7e, коли всі рішення секції розв'язані й ADR спавнені.

## Спавн ADR усередині 7d

Коли blast-radius gate спрацював на Прийнятому рішенні:

1. **Порахувати номер — по обох теках ADR:**

   ```bash
   ls docs/adr/*.md docs/features/*/adr/*.md 2>/dev/null \
     | xargs -n1 basename | grep -oE '^[0-9]{4}' | sort -n | tail -1
   ```

   Плюс один, з нулями до чотирьох знаків. Порожній вивід → `0001`. Нумерація наскрізна на
   весь репозиторій: `docs/adr/` тримає рішення рівня системи, `docs/features/<slug>/adr/` —
   рішення фічі, і номер «ADR 0007» має бути однозначним у будь-якому з них.
   Рахувати `ls … | wc -l` **не можна** — це дасть 0001 у теці фічі й зіткнення номерів.

2. **Скласти ім'я файлу** з **рішення**, а не з проблеми, англійською kebab-case:
   `0007-serve-images-from-a-public-bucket.md` ✓ проти `0007-image-access.md` ✗.

3. **Скопіювати** `./templates/adr-template.md` у `docs/features/<slug>/adr/NNNN-<title>.md`
   і заповнити: Status = `Accepted`; Context (2-4 речення з секції); Decision drivers
   (якості §1, обмеження §2, рядки PRD); Considered options — усі опції, які реально
   показувалися, включно з відкинутими, **без страшменів**; Decision outcome (обрана опція
   плюс 1-2 речення чому); Consequences (Positive / Negative / Neutral — усі три);
   Links (PRD, sad.md §N, сусідній ADR). Тіло — українською.

4. **Дописати рядок у таблицю §9** в пам'яті:
   `| [NNNN](adr/NNNN-<title>.md) | <назва-рішення> | Accepted | §N |`.

5. **Окремого коміту немає** — файл ADR пишеться разом із секцією в 7e, а комітиться разом
   з усім у кроці 8.

6. **Дописати в лог спавнів ADR** (тільки в пам'яті):

   ```
   {adr_id: "NNNN", title: "<kebab англійською>", section: "§N", triggered_by: "DEC-§N-<id>"}
   ```

   Критик читає теку `adr/` сам; лог спавнів потрібен для звірки в межах проходу.

## Лог правок (обов'язковий)

Після кожного `Виправити` / `Викинути` / `Винести у відкрите питання` (але **не** після
`Прийняти`) — один запис:

```
{decision_id: "DEC-§N-<короткий-id>"   (напр. "DEC-§4-uploadPath", "DEC-§5-galleryOwner",
                                        "DEC-§10-QG1-verification"),
 action:      "edit" | "drop" | "save_as_oq",
 before:      "<опція / формулювання / серйозність дослівно до дії>",
 after:       "<дослівно після; для save_as_oq — текст рядка §11 з owner і due;
                для drop — null>",
 user_reason: "<обґрунтування користувача дослівно>"}
```

`Прийняти` в лог не потрапляє — це базова лінія. Лог є **єдиним** сигналом, за яким критик
кроку 8 бачить, що саме користувач змінив; без нього класи F1-F4 не мають входу.

Користувач не назвав причини для `Drop` або `Save as OQ` — перепитай один раз. Дослівне
формулювання має значення: критик судить за ним, чи не викинуло відкладення вектор, який
PRD §6, PRD §7 або idea-brief §13 назвали несучим.

Лог спавнів ADR ведеться **поруч** із логом правок, а не всередині: це різні сигнали. Лог
правок — узгодженість із тим, що вище за течією; лог спавнів — які файли з'явилися нижче.

## Умова виходу

Крок 7 завершено, коли:

- усі 12 секцій показані (7a) і пройдені (7b), по одному вирішенню на рішення;
- вміст кожної секції та її ADR **уже на диску** (7e);
- таблиця §9 закрита: кожен файл у `adr/` має рядок, кожен рядок веде на наявний файл;
- §11 містить рядок на кожне `save_as_oq` з обома заповненими полями — owner і due;
- лог правок закритий, незавершених записів немає.

Далі — крок 8, [critic-phase.md](./critic-phase.md).
