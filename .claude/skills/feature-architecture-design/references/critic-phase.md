# Критик і фіналізація — крок 8

## TL;DR

Крок 8 — окремий підагент **зі свіжими очима** (він не бачив діалогу з користувачем).
Дивиться готовий `sad.md` і шукає шість класів проблем:

| Клас | Що шукає | Простіше |
|---|---|---|
| **F1** | §4 обіцяє одне, §6 або §10 показують інше | стратегічна нитка зривається |
| **F2** | обсяг розповз за розмір фічі | фіча виросла під час проходу |
| **F3** | відкладене або викинуте рішення зачіпає несучий вектор PRD | відклали ключове |
| **F4** | текст у файлі ≠ те, що користувач підтвердив | тихі правки після Socratic |
| **F5** | шаблонні заглушки, порожні секції, сироти ADR | структурні дірки |
| **F6** | числа не з PRD; страшмен в ADR; §2 суперечить конвенції без застереження | протиріччя з джерелами |

Після критика — регексні перевірки, Self-check і **єдиний коміт**.

Тіло промпту — у [critic-prompt.md](./critic-prompt.md). Цей файл — контракт диспатчу,
цикл вирішення й регексні перевірки навколо нього.

## Диспатч

Один виклик `Agent`, `subagent_type: "general-purpose"`, **чистий контекст**: підагент не
бачив діалогу, не бачив читання репозиторію, не має жодного попереднього стану skill-а.

**Що підставити у плейсхолдери** `critic-prompt.md`:

1. `{{SAD_DRAFT}}` — повний текст `sad.md`, щойно дописаного в кроці 7e.
2. `{{EDITS_LOG}}` — масив записів логу правок.
3. `{{ADR_SPAWNS_LOG}}` — масив `{adr_id, title, section, triggered_by}`.
4. Шляхи — **тільки шляхи, не тіла**: `{{PRD_PATH}}`, `{{CONTEXT_PATH}}`,
   `{{IDEA_BRIEF_PATH}}`, `{{ADR_DIR_PATH}}`, `{{REPO_DOCS}}` (`ARCHITECTURE.md`,
   `CLAUDE.md`, `SPEC.md`). Критик читає їх сам, у чистому контексті — переказ отруює оцінку.

## Контракт виходу

Звіт у markdown, ≤300 слів. Або літерал `NO_CONTESTED_DECISIONS`, або 0-7 знахідок, по
одному булету на кожну, з посиланням на §SAD плюс §PRD / рядок CONTEXT / файл ADR і
запропонованим вирішенням.

Повернув `CRITIC_BLOCKED: <причина>` (не зміг прочитати PRD, CONTEXT, теку ADR) — **зупинись
і скажи користувачеві**. Не комітити мовчки.

## Цикл вирішення

Кожна знахідка показується користувачеві через `AskUserQuestion` з опціями:

- **`Прийняти правку критика`** — застосувати запропоноване дослівно.
- **`Прийняти, інше формулювання`** — користувач дає своє; застосовується воно.
- **`Override (обґрунтування)`** — `sad.md` лишається як є, користувач називає причину.

Обмеження:

- **≤2 порції `AskUserQuestion`**, не більше 4 питань у порції. Друга відповідь по знахідці
  остаточна — та сама межа, що й у кроці 7.
- **`Override` дописує булет** у §1 ¶4 «Decision overrides», дослівно:
  «<заголовок знахідки> — перекрито автором, обґрунтування: <причина>». Це робить свідомий
  вибір видимим для етапів 08, 10 і 13, які читають цей документ як джерело.

Після вирішення всіх знахідок — Self-check із SKILL.md. Щось падає — одне повторне
`AskUserQuestion`, далі рухаємось далі.

## Регексні перевірки перед комітом

Незалежно від критика, по `sad.md` і теці `adr/`:

### Mermaid

Для кожного блоку ```mermaid у §3 / §5 / §6:

- блок має закривальні трилапки (не обрізаний);
- усі елементи (`Person`, `Person_Ext`, `Container`, `ContainerDb`, `System`, `System_Ext`,
  `SystemDb`, актори `sequenceDiagram`) оголошені **до** рядків `Rel(...)` і стрілок `->>`,
  які на них посилаються;
- немає `Container_Bondary` і `ContainerBoundary` — Mermaid на цих одруках мовчки малює
  порожній блок;
- немає `<placeholder>` із шаблону (`Person(user, "<User>", "<роль і намір>")`).

Влучання → `AskUserQuestion` по блоку: `Перегенерувати з CONTEXT і кроку 3` / `Override`.

### Формат назв ADR

Для кожного `docs/features/<slug>/adr/NNNN-*.md`:

- ім'я збігається з `NNNN-<kebab>.md`, `NNNN` — чотири цифри з провідними нулями;
- номер продовжує наскрізну нумерацію репозиторію — не збігається з жодним номером у
  `docs/adr/` і в інших теках `docs/features/*/adr/`;
- назва читається як **рішення** в наказовій формі, а не як тема. Ознака теми: доменний
  іменник без дієслова (`0007-image-access.md` ✗ проти
  `0007-serve-images-from-a-public-bucket.md` ✓);
- `Status: Accepted`, а не `Proposed`;
- посилання в `## Links` — markdown, не `[[wiki]]`, і ведуть на наявні файли.

Влучання → `AskUserQuestion`: `Перейменувати (пропозиція: <kebab>)` / `Лишити як є (обґрунтування)`.

### Сироти §9

- кожен файл у `adr/` має рядок у таблиці §9;
- кожен рядок §9 веде на наявний файл.

Влучання → `AskUserQuestion` на виправлення: дописати рядок / прибрати примарний / знайти файл.

## Коміт

Після проходження перевірок — **один коміт на весь прохід**:

```
NN: SAD + ADR for <slug> via feature-architecture-design
```

`NN` — наступний номер після останнього коміту з таким префіксом (`git log --oneline -20`).
Slug підставляється обов'язково. Тіло називає: обсяг документа (і що саме винесено в
наступну поставку, якщо фіча розділилася), перелік ADR по рядку на файл, свідомі розходження
з підписаними документами з §11.

## Режими відмови

- **Критик упав або не відповів** → зупинись і повідом. Тихого коміту не буває.
- **Критик повернув сміття** (ні булетів, ні `NO_CONTESTED_DECISIONS`, ні `CRITIC_BLOCKED`)
  → передиспатч один раз із доданим рядком «твій попередній вивід не відповідав формату».
  Знову сміття → зупинись і спитай користувача.
- **Користувач обрав `Override` на всі знахідки** → це його право; кожен `Override` лишає
  булет у §1 ¶4, тож слід перекриттів лишається видимим.
- **Регекси влучили 5+ разів** → це ознака, що pre-Socratic hygiene кроку 6 не спрацювала
  (див. [draft-generation.md](./draft-generation.md)). Скажи про це як про аномалію процесу
  й спитай, чи переробляти секцію. Переробка однієї секції — нормально; повний перезапуск
  кроку 7 — ні, це занадто.
